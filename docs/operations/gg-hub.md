# GG HUB 독립 중앙 사이트

GG HUB는 K-LOL/NEXUS와 나란히 배포되는 중앙 관리 서비스다. 자식 사이트 안에 들어가는 메뉴가 아니다. 같은 소스를 재사용하지만 별도의 Vercel 프로젝트, Neon 프로젝트, DB, 인증 키, 쿠키와 JWT 발급자를 사용한다.

| 대상 | 운영 주소 | 데이터 소유 |
|---|---|---|
| GG HUB | https://gg-community-hub.vercel.app | 사이트 소개·방 설정·중앙 관리자 |
| K-LOL.GG | https://k-lol-gg.vercel.app | 기존 회원·모집·경기 |
| NEXUS.GG | https://nexus-gg-kr.vercel.app | 기존 회원·모집·경기 |

## 실행·배포

- `NEXT_PUBLIC_SERVICE_ID=hub`를 **빌드와 실행 모두**에 사용한다. 기존 NEXUS 빌드에 런타임 변수만 바꾸면 안 된다.
- `.env.hub.example`을 기준으로 전용 비공개 환경을 준비한다. `HUB_DATABASE_URL`은 필수이며 기존 두 사이트 DB로 대체하지 않는다. 별도 Neon 프로젝트를 사용한다.
- `SESSION_SIGNING_KEYS`, `TOTP_ENCRYPTION_KEYS`, `V2_AUTH_RATE_LIMIT_PEPPER`는 신규 생성한다. 기존 서비스 키를 복사하지 않는다. 현재 TOTP 서비스는 기존 코드에서도 폐기 상태다.
- 새 DB만 `scripts/hub/bootstrap.ts`로 초기화한다. `HUB_BOOTSTRAP_CONFIRM=CREATE_EMPTY_HUB`, 정확한 `HUB_DATABASE_NAME`, 비공개 `HUB_ADMIN_LOGIN_ID`/`HUB_ADMIN_PASSWORD`가 필요하다. 기존 계정이 있거나 다른 브랜드 DB면 중단한다.
- 초기 관리자는 독립 계정이다. `/login`에서 최초 비밀번호를 바꾼 뒤 `/admin/login`으로 접속한다. 재실행해도 기존 비밀번호·수정된 등록 정보를 초기화하지 않는다.
- Vercel 배포는 **명시적인 `--project gg-community-hub --local-config vercel.hub.json`**으로 한다. 작업 디렉터리의 기존 NEXUS `.vercel/project.json`을 덮지 않는다. 허브에는 자식 사이트 cron을 등록하지 않는다.
- 허용 목록 밖의 게임·카카오·기존 사이트 설정 API는 404로 차단한다. 일반 중앙 관리자 화면은 자식 회원·경기 자료를 직접 조회하지 않는다. 전용 개설 작업만 검증된 신규 자원의 초기화·설정 게시를 수행한다.

## 기존 운영 제공 범위 (0.1.0)

공개 사이트 목록과 방문 링크, 중앙 최고 관리자의 사이트·방 추가/수정/보관, 사이트별 모집 그룹 설정을 제공한다. 초기 설정은 실제 운영 중인 두 사이트와 사용자가 지정한 네 방이다. 방 개수는 두 개로 고정하지 않으며 사이트 100개·방 500개 한도 내에서 추가할 수 있다.

초기 등록 기능의 상태는 실제 API 연결 상태가 아니다. 기존 K-LOL/NEXUS 등록은 `UNVERIFIED`와 `NOT_APPLIED`를 유지하며 휴대폰 봇 설정·회원 소속·모집 원본을 변경하지 않는다. 신규 사이트 자동 개설은 아래 개설 스튜디오 0.1.1에서 별도로 제공한다.

## 후속 구현

1. 사이트 소유자 인증과 연결 설치·철회, 운영 상태 확인.
2. 양쪽 로그인으로 본인 계정 연결, 내 가입 사이트 모아보기.
3. 기기/방 고유 ID 연결과 서명된 동적 설정 배포. 기존 네 방 회귀 검증 후 방별 이관.
4. 범위별 정보 공유·연합·교류 게시판, 공동 대회.
5. 본인 확인된 계정에 한정한 운영 기록 공유, 출처·만료·이의·정정·조회 감사.

전체 설계는 [연합 허브 실행 계획](../architecture/community-federation-execution-plan.md)을 따른다. MMR 원본은 사이트별로 유지하고, 차기 산식은 [감사 보고서](../architecture/drafts/balance-mmr-audit-2026-10-29.md)의 shadow 평가를 먼저 수행한다.

## 장애·복구

중앙 서비스가 중단되어도 기존 K-LOL/NEXUS와 설치된 폰 봇은 독립적으로 운영된다. 허브 출시 이전으로 되돌려야 하면 허브 공개 도메인만 해당 허브의 검증된 배포로 전환한다. 자식 사이트 도메인이나 DB를 허브로 바꾸지 않는다. 최초 출시에는 이전 허브 배포가 없으므로 실패한 후보를 승격하지 않고 수정 재배포한다.

기존 0.1.0 배포는 migration 0050까지 사용한다. 개설 스튜디오의 추가 migration은 HUB와 신규 관리형 사이트에 적용하며 기존 K-LOL/NEXUS에 일괄 적용하지 않는다. 운영 DB를 지우는 down migration은 제공하지 않는다. 재배포·복구 시 중앙 등록 자료는 보존한다.

## 개설 스튜디오 운영 (0.1.1)

현재 운영 HUB의 자동 개설 연결과 예약 실행은 활성화되어 있다. 전용 토큰을 사용하는 실제 worker의 독립 사이트 준비와 검증용 자원 정리를 [0.1.1 QA](../qa-evidence/community-site-provisioning-enabled-2026-10-29/README.md)에서 확인한다. 가입·신청·SSO의 이전 검증은 [0.1.0 QA](../qa-evidence/community-site-studio-2026-10-29/README.md)에 보존한다. 운영자 이용 흐름은 [사이트 설정 안내](../product/gg-hub-site-settings-guide.md)에 있다.

전용 Vercel 토큰 `GG HUB site provisioning`은 2027-01-27 만료된다. 만료 전에 같은 팀·용도 범위로 교체하고 HUB의 민감 production 환경 변수와 배포를 갱신한 뒤 인증된 빈 worker 응답을 확인한다. 기존 요금제 사용량 비용은 허용되었으며 신규 월정액 구독이나 요금제 업그레이드는 수행하지 않았다.

`COMMUNITY_SITES_ENABLED=true`는 중앙 가입·신청·심사·설정 화면을 제공한다. 자동 개설은 별도 `HUB_PROVISIONING_ENABLED=true`와 `.env.hub.example`의 전용 공급자 자격증명·검증된 엔진 SHA가 모두 있어야 승인할 수 있다. 준비 표시만으로 공급자 권한·할당량·실제 개설 성공을 보증하지 않는다.

- Vercel·Neon 전용 연결 자격증명은 HUB 서버 환경에만 둔다. 새 사이트에는 해당 사이트 전용 DB·세션·SSO 키만 전달한다. CLI 개인 로그인 토큰을 서버 토큰으로 대체하지 않는다.
- 엔진은 `HUB_ENGINE_GIT_REF`에 지정한 정확한 Git SHA로 배포한다. 현재 검증된 신규 사이트 엔진은 `7d669ec5bc2af56ab23c793f9a530bf5f6fbfc82`이며 HUB 서버 소스 `ce31ea2c68192093700a79bda5d0add3cb3e77c0`와 구분한다. 수정한 브랜치의 최신 코드를 자동으로 따라가지 않으며 이미 시작한 작업의 엔진·설정 스냅샷은 바꾸지 않는다.
- HUB의 보호된 cron은 한 번에 한 작업 단계만 실행한다. 개설·게시·공개 요청은 DB 작업 목록에 저장되며 재시도는 기존 자원과 설정 스냅샷을 사용한다.
- `vercel.ts`는 신규 관리형 사이트에 전용 키로 보호된 경기 통계·MMR·대회 평가·보존 작업을 등록하며, 연결되지 않은 Riot·카카오 작업은 제외한다. 기존 K-LOL/NEXUS의 예약 목록은 보존한다. HUB CLI 배포는 명시적으로 `vercel.hub.json`을 사용한다.
- 승인 시 새 DB는 비어 있어야 하며 원본 자료를 복제하지 않는다. 새 사이트의 소유자 연결만 생성한다. 다른 사이트의 DB·공급자 자원 식별자가 발견되면 개설을 중단한다.
- 실패한 개설은 관리자 화면에서 사유와 단계를 확인한 뒤 같은 작업을 재개한다. 자동 정리로 DB·배포를 삭제하지 않는다. 실제 사용 자료가 있는 자원은 복구 기준을 확인한다.
- 중앙 장애 중에도 공개 완료된 자식 사이트는 자기 DB와 인증 세션으로 운영한다. 새 중앙 로그인·신청·설정 변경은 중앙 복구를 기다린다.

공개 쓰기 승인은 작업자가 승인된 소유자의 요청을 가져오는 시점에 확정한다. 이후 제재가 이미 완료된 외부 공개를 되돌리지는 않는다. 응답이 유실되면 `ACTIVATING`을 유지하며 최대 15분 간격으로 같은 자원의 결과를 재확인한다. 이때 소유자 권한이 중지되었다면 `OBSERVE_ONLY`로 조회만 수행한다. 자식의 사이트·소유자 연결·설정 revision과 `ACTIVE`가 모두 일치해야 중앙도 공개 완료로 기록한다. 새 DB 생성이나 자동 비공개·삭제로 보상하지 않는다. 예약 작업 실행 한도는 180초, 작업 lease는 240초다.

신규 Riot 연결, 기존 사이트 계정 연결, 동적 휴대폰 라우팅, 제휴·공유·공동 대회는 별도 완료 검증 전까지 기능이 제공된 것으로 공지하지 않는다.

## 관리형 사이트의 기능 추가·종료 절차

다음은 신규 관리형 사이트 구현의 기능 카탈로그를 변경할 때 적용하는 절차다. 운영 배포 여부는 해당 릴리스의 배포 근거에서 별도로 확인한다.

- 선택 기능을 추가할 때 기존 저장 설정에 해당 ID가 없으면 `false`로 정규화한다. 이미 저장된 `true`·`false` 값과 홈 배치는 유지한다. 신규 사이트 생성 화면의 기본값을 기존 사이트에 덮어쓰거나 새 기능을 자동으로 켜지 않는다.
- 배포는 새 ID를 이해하는 공통 엔진을 대상 사이트에 먼저 적용한 뒤 HUB의 기능 선택지를 노출하는 순서로 진행한다. 새 ID를 모르는 구버전 사이트에 새 키가 포함된 설정을 게시하지 않는다. 구버전 엔진으로 복구할 때도 저장 설정의 호환성을 먼저 확인한다.
- 필수 `members` 설정 누락, 알 수 없는 ID, boolean이 아닌 값, 충족되지 않은 의존성은 계속 거부한다. 기존 기능에 새로운 필수 의존성을 추가하거나 필수 기능·설정 구조를 바꾸려면 먼저 저장 설정을 안전하게 이전하는 migration과 호환성 검증을 준비한다.
- 기능을 종료할 때는 먼저 메뉴·선택지에서 숨기고 신규 생성·신청을 차단한다. 저장된 ID를 즉시 카탈로그에서 지우거나 원본 자료를 삭제하지 않는다.
- 기존 참가 취소, 진행 중인 경기·대회의 결과 확정, 운영진의 관리와 자료 내보내기 경로를 유지한다. 운영자가 남은 작업과 보존할 자료를 확인한 뒤 종료 일정을 확정한다.
- 마지막으로 저장된 기능 설정·홈 블록·의존성을 이전하는 전진 migration을 작성하고, 구버전 설정 읽기와 복구 경로를 검증한다. 적용 대상 사이트의 이전 완료를 확인한 다음 카탈로그 ID와 관련 코드를 제거한다. 자료 삭제는 이 과정에 자동으로 포함하지 않는다.

검증 근거는 `tests/community-site-configuration.test.ts`의 기존 설정 호환성·자동 활성화 금지·필수값·의존성 테스트로 유지한다. 아직 사용처가 없는 플러그인 실행기나 폐기 기능 레지스트리는 만들지 않는다.
