# ADR 0011 설계안: 편집 가능한 파티 양식과 저장 후 전체 구인 목록

- 작성: 2026-09-21 / 설계 버전 1.0
- 상태: **사용자가 N인 파티 설계 흐름을 수용함. 2026-09-22 편집·충돌 병합·오류 안내 관련 범위는 운영 적용 및 읽기 검증 완료. 새 목록 UX·직접 상세 조회·초안 마감 등 전체 설계 구현은 남아 있음.** [부분 구현·운영 QA](../qa-evidence/kakao-copy-reliability-v1.0.1-2026-09-22/README.md)
- 범위: `N인파티`로 만드는 번호형 파티. 내전의 회원 연결 정책은 이 문서의 변경 범위가 아니다.
- 사용자 확정: 양식에서 이름 추가·삭제, 시작·게임 수정 모두 허용. `3ㅉ`처럼 파티 번호를 붙여 마감.
- 기존과의 관계: 구현 시 ADR 0010의 파티 추가 전용 정책과 저장 후 최신 양식 응답을 대체한다. 기존 문서는 당시 결정 기록으로 보존한다.

## 1. 사용자 흐름

`5인파티` → 빈 양식 → 작성 후 전체 전송 → 등록 완료 + 현재 구인 목록 → `구인상세 3` → 최신 양식 편집·전체 전송 → 수정 완료 + 현재 구인 목록 → `3ㅉ` → 마감 완료 + 남은 구인 목록.

생성·상세는 편집할 **양식**을, 저장·마감·현황은 **구인 목록**을 보여준다. 참가자에게 주최자 이름이나 별도 가입을 요구하지 않는다. 사이트에는 같은 파티의 현재 내용이 반영된다.

## 2. 빈 양식 시안

줄 구획은 코드 아래의 얇은 선 한 줄과 빈 줄로 통일한다. 메타정보·이름 바로 아래에 장식선을 넣지 않는다. 현재 파서는 다음 줄 입력도 값으로 인식하므로, 구분선이 게임명이나 참가자 이름이 되는 일을 피한다.

```text
[파티 #3] 5인 파티 · 0/5명
양식코드: L44EK-2X9AW
──────────────
시작 시간 :
게임 종류 :

1.
2.
3.
4.
5.

예비 1.
```

- 양식코드는 항상 제목 바로 아래에 둔다. 복사 대상 안에 포함하되 별도 입력을 요구하지 않는다.
- 생성 시 시작·게임은 빈칸이다. 참가 슬롯은 정원만큼, 예비는 첫 빈 번호까지 표시한다.
- 인원수는 사용자가 수정하지 않아도 서버가 저장된 이름으로 계산한다.
- 긴 이용 방법은 기본 양식에 넣지 않고 도움말·오류 응답에 둔다.
- 구분선은 표시 전용이다. 제거하거나 줄바꿈이 CRLF로 바뀌어도 같은 내용으로 읽혀야 한다.

작성 예시는 `시작: 21:00`, `게임: 증칼`, `1. 참가자A`다. 사용자 예시의 `시작: 증칼`을 자동으로 `21:00`으로 바꾸지는 않는다. 시간·조건 문구는 입력한 뜻을 보존한다. 시작 시간, 게임 종류에 미입력시 미입력이라고 저장

## 3. 저장 후 응답 시안

```text
✅ 파티등록 완료 · #3 · 유저A

📋 현재 구인

[파티 #1] 2인 파티 · 모바시 · 듀랭 · 1/2명
└ 구인상세 1

[파티 #2] 4인 파티 · 모바시 · 배그 · 3/4명
└ 구인상세 2

[파티 #3] 5인 파티 · 21:00 · 증칼 · 1/5명
└ 구인상세 3
```

| 상황 | 첫 줄 | 뒤에 붙는 내용 |
|---|---|---|
| 최초 등록 | `✅ 파티등록 완료 · #3 · 유저A, 유저B` | 현재 구인 목록 |
| 이름·시간·게임 변경 | `✅ 파티수정 완료 · #3` | 변경 반영된 현재 구인 목록 |
| 같은 내용 재전송 | `이미 같은 내용으로 저장되어 있어요.` | 현재 구인 목록 |
| `구인현황` | `📋 현재 구인` | 현재 구인 목록 |
| `구인상세 3` | 파티 양식 제목 | 현재 값·이름·최신 양식코드가 들어간 편집 양식 |
| `3ㅉ` | `✅ 파티 #3 마감 완료` | #3이 빠진 현재 구인 목록 |
| 모집 없음 | `📋 현재 구인` | `현재 모집 중인 파티가 없습니다.` |

목록은 번호순이며, 한 파티는 요약 한 줄과 상세 명령 한 줄로 구성한다. 주최자·참가자 전체 이름·기존 구인중/대기중/진행중/대형 그룹은 넣지 않는다. 예비가 있으면 요약 끝에 `· 예비 1명`을 추가한다.

`모바시`는 그대로 표시한다. 시간이 지났거나 정원이 찼다는 이유만으로 목록에서 제거하지 않는다. 실제 마감 또는 기존 운영일 종료 정책이 기준이다. 긴 시간·게임은 요약에서만 말줄임하고 상세 양식·저장 값은 보존한다.

## 4. 편집 규칙

| 사용자가 양식에서 한 일 | 설계 동작 |
|---|---|
| 빈 번호에 이름 입력 | 참가 추가, 실제 인원 재계산 |
| `2. 이름`을 `2.`로 변경 | 해당 참가 삭제 |
| 기존 이름을 다른 이름으로 변경 | 현재 값이 원본과 충돌하지 않으면 교체 |
| 시작·게임 내용 변경 | 충돌하지 않으면 변경 반영 |
| 시작·게임 값을 빈칸으로 변경 | 값을 비움. 양식은 빈칸, 현황은 `미정` 표시 |
| 예비 이름 추가·삭제 | 예비 명단 변경. 자동 본 참가 승격 없음 |
| 예비에서 본 참가로 직접 이동 | 양쪽 변경을 함께 검증하고 빈 본 참가 자리가 있을 때만 원자 반영 |
| 모든 이름 삭제 | 등록된 파티를 0명으로 유지. 파티 마감은 `3ㅉ` |
| 번호 행 자체를 없애거나 양식을 일부만 전송 | 삭제 의도로 추정하지 않고 최신 양식 안내 |
| 번호·정원·양식코드 변경 | 저장 거부. 다른 모집으로 바꾸지 않음 |
| 이름 없이 생성 직후 빈 양식 그대로 전송 | 게시하지 않고 첫 이름 입력 안내 |

처음 공개 등록은 최소 한 명의 이름이 들어간 전송 시점이다. DRAFT는 현황에 나오지 않지만 `구인상세 3`으로 다시 받을 수 있어야 한다. 같은 방의 편집 권한 정책을 유지하며, 현재 시스템에서 발신자별 소유자 권한을 새로 추정하지 않는다.

이 문서의 방 범위는 기존 인증된 프로필·설치의 논리 scope다. 실제 카카오톡 방 이름이나 발신자 표시명을 인증 근거로 추가하지 않는다.

## 5. 동시 작성과 오래된 양식

양식코드로 원본을 찾고, 원본·현재 저장 값·제출 값을 transaction 안에서 비교한다.

- 제출 값이 원본과 같으면 사용자가 바꾸지 않은 항목이므로 현재 값을 보존한다.
- 현재 값이 원본과 같으면 사용자의 변경을 반영한다.
- 현재 값과 제출 값이 같으면 이미 반영된 변경으로 처리한다.
- 같은 항목을 서로 다르게 바꿨으면 전체 저장을 거부하고 최신 양식을 보여준다. 일부만 저장하고 성공처럼 안내하지 않는다.
- 서로 다른 항목의 변경은 병합한다. 다른 사람이 새로 참가한 이름을 옛 양식의 빈칸으로 지우지 않는다.
- 일반 번호형 파티의 같은 빈칸 동시 추가는 새 참가자를 현재의 다음 빈칸에 넣는다. 정원을 넘으면 자동 예비 이동 없이 예비 선택을 안내한다.
- 삭제 후 슬롯을 자동으로 당기지 않는다. 이미 취소된 원본 참가자는 옛 양식으로 되살리지 않는다.
- 동일 이름 중복, 정원 초과, 다른 방·다른 파티·다른 운영일의 코드, 마감 후 코드 재사용을 차단한다.
- 양식코드는 성공 후 상태가 바뀌면 새 원본 상태를 가리킨다. 다음 상세 조회에서 최신 코드를 반환한다. 인원·코드는 사용자 입력으로 신뢰하지 않는다.

## 6. 마감과 오류 응답

`3ㅉ`는 공개 목록에서 해당 파티를 마감한다. DB 기록을 물리 삭제하지 않는다. 작성 중 DRAFT도 같은 명령으로 취소할 수 있어야 한다. 번호 없는 `ㅉ`는 대상을 추정하지 않고 번호를 붙이도록 안내한다.

충돌 시:

```text
저장하지 않았어요. 같은 항목을 다른 사람이 먼저 수정했어요.
아래 최신 양식을 복사해 다시 작성해주세요.

[최신 편집 양식]
```

저장은 성공했지만 목록 조회가 실패한 경우:

```text
✅ 파티등록 완료 · #3

현재 구인 목록을 불러오지 못했어요.
구인현황을 입력해 주세요.
```

연결 오류는 저장 실패와 같지 않다. 휴대폰에서 응답을 못 받았다면 `구인상세 3`으로 현재 상태를 확인한다. 새 event 재전송도 중복 참가·중복 파티를 만들지 않도록 한다.

## 7. 구현 범위와 현재 증거

읽기 기준 소스: `413825f0` (2026-09-21 R24 이름 우선 내전 패치의 기록 커밋).

| 구성 | 현재 코드 근거 | 필요한 변경 |
|---|---|---|
| R24 휴대폰 전송 | public 설치본 `handleCopyRosterForm`, 원문 전달 | 헤더·번호행 유지. 코드 상단 이동·빈칸 배치에 추가 폰 수정은 필요하지 않은 구조. 실제 새 양식 런타임 검증은 구현 단계 |
| 빈 양식·상세·현황 출력 | `kakao-v4/v1-strict-party-replies.ts` | 제안 시안, 번호순 두 줄 요약, 입력한 모바시 표시 |
| 전체 편집 저장 | `application/command-handler.ts`, `party-copy-snapshot.ts` | 현재 추가 전용·메타 변경 금지를 항목별 병합으로 대체 |
| 저장 후 현황 | `kakao-v4/dispatcher.ts` | 기존 `appendLatestPartyStatus`와 조회 실패 fallback 재사용 |
| 직접 상세 조회 | `postgres-kakao-assistant.ts`, dispatcher | 현황 20건 안에서 찾는 방식 대신 번호·scope·운영일로 직접 조회. DRAFT 상세 허용 |
| 현황 조회 | `postgres-kakao-assistant.ts` | 20건 잘림을 제거하고 대상 전체를 조회. 요약 조회에서 불필요한 모든 양식코드 발급 제거 |
| 마감 | `application/commands.ts`, domain transition | 진행 중은 마감, DRAFT는 취소. 기존 이력·감사 기록 보존 |
| 사이트 | 동일 파티 저장소·조회 | 새 편집 결과·인원·마감 상태를 같은 데이터로 표시 |

스키마·휴대폰 파일 변경 없이 기존 snapshot/transaction/명령 경로를 확장하는 것을 목표로 한다. 기존 R22 문서의 전체 덮어쓰기 계약을 현재 구현이라고 인용하지 않는다. 최신 사용자 결정과 실제 R24 코드의 차이는 본 문서에 명시했다.

## 8. 구현 완료 조건

1. 생성·상세·복붙·현황·`Nㅉ`를 기존 R24 런타임으로 검증한다. 공개/private 폰 SHA-256을 전후 비교한다.
2. 신규 등록, 이름 삭제·교체, 시간·게임 비움/변경, 예비 추가·이동, 0명 유지, 빈 양식 실수 전송을 합성 데이터로 검증한다.
3. 서로 다른 변경 병합·같은 항목 충돌·동일 칸 동시 추가·취소자 재등장 방지·event 재전송을 DB에서 검증한다.
4. 활성 21개 이상에서도 누락 없는 목록과 모든 번호의 직접 상세를 검증한다. 긴 목록의 응답 크기·전송 가독성과 R24의 5초 단일 요청 제한을 확인한다. 제한 초과가 관측되면 누락 없이 표시하는 방식을 확정한 후 배포한다.
5. 저장 후 현황 조회 실패와 휴대폰 응답 실패를 구분하고, 사이트에서 동일 변경·마감 상태를 확인한다.
6. 전체 검사·빌드 후 기능 버전·tag·QA·배포 증거를 등록한다. 현재 설계 문서는 운영 기능 완료 증거가 아니다.
