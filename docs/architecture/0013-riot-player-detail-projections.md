# 0013: Riot 플레이어 상세 projection 확장

상태: 2026-09-25 운영 적용. Drizzle `0045_simple_reptil`, 최종 전체 검사와 배포는 [릴리스 QA](../qa-evidence/riot-player-detail-v1.0.0-2026-09-25/README.md)에서 확인한다. 전체 회원 연결과 상세 이력 수집은 별도 진행 상태로 기록한다.

관련 범위: [플레이어 상세 기능 대응표](../parity/RIOT_PLAYER_DETAIL_PARITY.md).

## 배경

확장 전 플레이어의 Riot 탭은 현재 랭크 중심이었다. 기존 최근 솔로 JSON은 팀 밸런스 보조 데이터로 사용하는 8필드 집계이며, 경기별·챔피언별·일자별 상세나 LP 관측 이력을 표현하지 못한다. 사용자는 참고 소환사 상세의 전적·챔피언·빌드·리포트 기능 전체를 요구했다.

기존 연결·동기화 작업·권한·공개 상태 경계는 재사용한다. 페이지 렌더링 시 Riot API를 여러 차례 직접 호출하는 방식은 응답 지연과 호출량을 키우므로 저장된 공개 projection을 조회하도록 확장한다.

## 구현 결정

### 1. 수집 데이터와 공개 데이터의 경계를 유지한다

- `riot-match-normalizer.ts`는 경기·참가자·timeline에서 허용한 필드만 추출한다. 원본 provider JSON, PUUID, 토큰을 새 전적 테이블이나 공개 DTO에 보존하지 않는다. 저장된 JSON도 조회할 때 중첩 필드의 허용 목록으로 재검사한다.
- 참가자 상세에는 공개 Riot ID와 경기 성과가 들어간다. 공개 화면은 다른 참가자의 이름을 기본 익명 처리한다. 이는 화면 표시 설정이며 API의 Riot ID를 비공개로 만드는 권한 기능은 아니다. 함께 만난 소환사는 관측된 Riot ID로 집계하므로 Riot ID 변경 전후의 동일인을 추측하여 합치지 않는다.
- 현재 연결 상태 `CONNECTED`, 연결 소유자, 등록된 정규화 Riot ID, 플레이어 `ACTIVE`, 연결 revision을 조회 경계에서 확인한다. 랭크 요약의 동기화 시각도 연결 시각 이후여야 한다. 재연결 후 이전 계정의 기록이 새 계정에 표시되지 않도록 한다.
- 작업 완료 시 기존 애플리케이션의 현재 연결/revision 검증을 통과한 트랜잭션에서만 projection을 저장한다. 다른 revision의 저장 자료는 공개 조회 대상에서 제외하고 다음 정상 저장 시 정리한다.
- 사용자 지정 경기·Tournament 공개에는 별도의 동의 경계가 필요하다. 이 일반 전적 기능은 동의를 대신하지 않는다. 수집 시 `gameType === MATCHED_GAME`과 공식 공개 LoL 큐 allowlist를 모두 검사한다. `queueId=0`, custom, tutorial, practice tool, TFT, Swarm, 미등록 신규 큐는 제외한다. 저장 parser도 큐 allowlist를 다시 검사한다. 제외가 확인된 경기의 시각은 이력 cursor 이동에만 사용하고 경기 내용을 저장하지 않는다.
- 현재 허용 큐는 `400, 420, 430, 440, 450, 480, 490, 700, 720, 870, 880, 890, 900, 1020, 1300, 1400, 1700, 1710, 1900, 2300, 2400`이다. Riot의 [공식 큐 목록](https://static.developer.riotgames.com/docs/lol/queues.json)을 확인한 기준이며, 새 큐를 자동 공개하지 않는다.

### 2. 최근 솔로 요약과 상세 전적은 별도 계약이다

- 기존 `RiotRecentSoloSummary`의 의미·20경기 상한·8필드 검증을 유지한다. 상세 전적 필드를 추가해서 기존 parser의 extra-key 방어를 완화하지 않는다.
- 상세 DTO는 경기 ID, 시작 시각, 길이, 큐·맵·패치, 참가자, 팀, 정제한 timeline과 수집 상태를 가진다. 공개 응답은 수집 시각, 최근 180일 범위의 저장 경기 수·최초/최종 경기 시각·이력 수집 완료 여부·다음 cursor를 별도로 제공한다. 이 계약에는 현재 별도 DTO version 필드가 없으며 저장 parser와 타입이 구조를 고정한다.
- 전체 랭크 승패, 최근 상세 표본, 사이트 내전 통계를 서로 합산하지 않는다.
- 선택 지표의 부재는 `null` 또는 명시적 미제공 상태다. 정상적으로 관측된 0과 구분한다. 다시하기는 경기 목록에 남지만 성적·빌드 집계에서는 제외한다.
- 프런트엔드 필터·집계는 **현재 불러온 경기**에 적용한다. DB에 저장된 경기 수와 브라우저에 불러온 경기 수를 함께 표시하여 첫 40경기를 전체 시즌 분석으로 오인하지 않게 한다.

### 3. 무제한 실시간 수집 대신 예산이 있는 동기화를 사용한다

- 기존 signed worker, lease, 멱등 처리, 연결 revision, 재시도/`Retry-After`를 재사용한다. 예약 갱신 대상은 마지막 요청으로부터 6시간이 지난 연결이다. 이는 이력 수집을 빠르게 끝내기 위해 호출 제한을 우회하는 작업이 아니다.
- 한 수집 증분은 솔로 랭크 20경기 ID, 최근 180일의 최신 20경기 ID, 이전 cursor의 10경기 ID를 조합한다. 경기 ID 중복을 제거하고 캐시를 재사용한다. 저장 캐시는 최신 120경기와 timeline 대기 중인 최대 20경기를 합쳐 읽는다.
- analytics provider 호출에는 전체 25초 예산과 최대 동시 2요청을 둔다. 상세 응답 상한은 512 KiB, timeline은 2 MiB다. timeline은 한 증분에서 최대 4경기를 추가 수집한다. 429 응답을 받으면 이후 요청을 중단하고 `Retry-After`를 다음 시도로 넘긴다.
- 경기와 timeline은 독립적인 성공 여부를 가진다. `PENDING`/`AVAILABLE`/`UNAVAILABLE`을 구분하고, 이미 저장된 `AVAILABLE` timeline을 후속 부분 수집 결과로 덮어 지우지 않는다. timeline은 최대 241프레임·8,000이벤트를 검증한다.
- HTTP/JSON 전달 실패는 `PENDING`으로 재시도한다. 정상 JSON이지만 지원하지 않는 timeline 계약이면 `UNAVAILABLE`·부분 수집으로 기록하여 같은 최신 4경기가 다른 경기 수집을 영구적으로 막지 않게 한다.
- 이력 cursor는 필요한 경기의 처리 결과가 확인된 경우에만 이동한다. 최신 20경기가 기존 캐시와 전혀 겹치지 않으면 중간 누락을 막기 위해 이력 진행점을 되돌려 다시 수집한다. 일부 실패나 이력 수집 중 상태를 시즌 전체 완료로 표현하지 않는다.
- 최신 20경기가 모두 공개 제외 경기이면 원본을 저장하지 않아 캐시 중복 검사만으로는 같은 페이지인지 알 수 없다. `analytics_progress.updated_at`에 마지막으로 최신 페이지 전체를 검증한 시각을 보존하고, 이를 기준으로 이미 확인한 제외 페이지가 이력 진행을 반복 초기화하지 않게 한다. 최신 페이지가 부분 실패하면 이 시각을 갱신하지 않는다. 첫 부분 실패나 revision 변경 시 내부 epoch 값을 사용하며 공개 응답에는 1970년을 표시하지 않는다. 공개 갱신 시각은 이 검증 시각과 실제 archive의 최근 수집 시각 중 최신값이다.
- 공개 페이지 및 상세 API는 DB projection만 읽는다. 첫 페이지는 최대 40경기이며 시작 시각과 경기 ID를 묶은 cursor로 이어 읽는다. 목록에서는 큰 timeline을 빼고 10/15분 비교 요약을 전달하며, 경기 펼치기 또는 빌드 분석 동작에서 저장된 timeline만 별도 조회한다.
- 관리자 목록에는 필터 전체 건수·현재 범위·이전/다음 페이지를 제공한다. `전체 동기화`는 페이지·필터와 별개로 연결된 전체 계정을 대상으로 한다. 미연결·연결 해제·해제된 자격은 연결을 먼저 복구해야 하며 목록 페이지의 인원과 동기화 대상 수를 혼용하지 않는다.
- `ALL` 동기화는 현재 연결 시각 이후의 pending 작업을 재사용하고, cooldown 중인 계정은 만료 시각으로 새 작업을 예약한다. 한 계정의 cooldown 때문에 다른 연결 전체 요청을 되돌리지 않는다. 단일/선택 동기화의 기존 cooldown 거절 계약은 유지한다.

### 4. 날짜별 랭크는 관측 이력으로 저장한다

League-v4 현재값에서 과거 LP를 복원하지 않는다. 랭크 projection을 저장할 때 관측 시각·티어·단계·LP·승패를 기록하며, `(연결 ID, revision, 한국 날짜)`마다 마지막 관측 하나를 upsert한다. 최근 180일 밖과 이전 revision의 관측은 정상 저장 시 정리한다. 동기화하지 않은 날짜의 값을 만들어 넣지 않는다.

갱신 전후 두 관측 사이에 여러 게임이 있을 수 있으므로 게임별 LP 획득/손실을 배분하지 않는다. 그래프는 티어·단계를 환산한 좌표를 사용하고 원래 티어·단계·LP를 수치 표에 남긴다. 마스터 이상은 공통 기준점 + LP다. 이 좌표는 Riot의 MMR이나 자체 랭킹이 아니다. 최초 관측 하나도 표시하며, 날짜·연도 필터만 LP 이력에 적용한다.

### 5. 해석 가능한 리포트와 표본을 제공한다

- 종합·챔피언·분석 리포트 탭은 연도, 게임 종류, 복수 패치, 포지션, 챔피언, 승패, 기간과 정렬을 공유한다. 연도 필터는 Riot 시즌 완료를 뜻하지 않는다.
- 모스트 챔피언, 라인 비율·승률·게임 수, 날짜별 성적, 함께 만난 소환사, 같은 포지션 상대, 경기 참가자·아이템·룬·주문·멀티킬을 실제 표본으로 계산한다. 같은 포지션의 상대가 하나로 식별되는 협곡 경기만 10/15분 골드·CS·경험치 비교 대상으로 삼는다.
- 경기 성장 차트는 관측된 골드·CS·경험치와 팀 골드 차이를 표시한다. 값이 없는 프레임을 0이나 선형 보간 값으로 바꾸지 않고 그래프와 수치 표를 함께 제공한다.
- 리포트는 성장(골드/분), 교전(킬 관여율), 오브젝트 피해/분, 시야 점수/분, 15분 골드 차이, 첫 15분 킬·어시스트 참여 횟수의 6개 지표다. 각 지표의 산식·유효 표본 수를 표시한다. 마지막 지표는 이동 경로를 이용한 로밍·갱킹 판정이 아니다.
- 최종 아이템·룬·주문 조합과 시작 아이템·신발·1~3코어·스킬 순서는 개인 표본의 빈도·승률이며 큐·맵별로 분리한다. 시작 아이템은 첫 90초 구매, 코어는 Data Dragon `16.17.1`의 정적 분류로 판정한다. 구매 취소를 되돌리며, 코어 채택률 분모에는 해당 코어 이전에 끝난 유효 timeline 경기도 포함한다. 고정 패치의 아이템 분류가 다른 패치까지 완전하게 대표한다고 주장하지 않는다.
- lol.ps의 비공개 인분·MVP·팀운·멘탈 점수, 지역/티어 전체 승픽밴율, 일반 사용자 대비 백분위는 구현한 개인 집계와 동등한 자료가 아니다. 해당 기능을 완료했다고 표시하지 않는다.
- 외부 AI 서비스나 유료 분석 API에 데이터를 보내지 않는다. 분석은 공개한 계산식에 따른 규칙 기반 결과다.
- 분석 저장은 `localStorage`에 같은 플레이어·Riot ID별 최대 10개를 보관한다. 필터, 경기 ID 목록, 생성/수집 시각, 집계, 산식 버전 `klol-observed-match-v1`을 보존한다. 참가자 원본·PUUID는 저장하지 않는다. 서버/다른 기기와 공유하지 않으며 이후 동기화로 기존 스냅샷을 바꾸지 않는다.

## 저장소 변경 검토

원본은 `src/platform/db/schema/riot.ts`이며 additive migration은 `drizzle/0045_simple_reptil.sql`이다. 기존 테이블을 재작성하지 않고 다음 3개 테이블을 추가한다.

| 테이블 | 저장 내용과 키 | 주요 제약 |
|---|---|---|
| `riot.analytics_progress` | 연결별 revision·이전 경기 cursor·수집 완료·최신 페이지 완전 검증 시각, PK `link_id` | revision/cursor 음수 금지, 연결 FK cascade |
| `riot.match_archive` | 정제한 경기 JSON과 시작/수집 시각, PK `(link_id, link_revision, match_id)` | 경기 ID 형식·JSON object·revision 검사, 연결 FK cascade |
| `riot.rank_history` | 한국 날짜의 마지막 랭크 관측, PK `(link_id, link_revision, day)` | 날짜 형식·음수가 아닌 LP/승패, 연결 FK cascade |

`riot_archive_page_idx`는 `(link_id, link_revision, started_at DESC, match_id DESC)` 순서다. JSON 내부의 상세 구조·필드 누출 방어는 domain parser가 수행하며 SQL의 object 제약만으로 충분하다고 보지 않는다.

`0045` fresh, 데이터가 있는 `0044`에서 upgrade, 재실행 no-op 검증은 격리 PostgreSQL에서 수행한 결과를 QA 증거에 연결한다. 운영 적용은 검토된 `0045` 한 개만 사용한다. 운영 journal의 과거 source 불일치는 preflight 증거에 보존하며 기존 migration을 다시 실행하여 맞추지 않는다.

운영 `0044`의 read-only `pg_dump`와 격리 로컬 restore는 완료했다. 운영 DB 복구 데이터를 `.private`에만 두고 공개 증거에는 집계·해시·경로만 기록했다. 이 백업 검증은 provider PITR 검증을 대신하지 않는다.

## 호환성·검증

1. 기존 public summary API 소비자가 새 상세 계약 때문에 실패하지 않는다.
2. 기존 recent-solo 요약과 팀 밸런스 보조 점수 회귀 검사가 통과한다.
3. 미연결·초기 동기화·오래된 자료·일시 오류·호출 제한·부분 수집을 각각 검증한다.
4. PUUID·토큰·원본 provider 응답을 공개 DTO에서 재귀적으로 탐지하는 테스트를 둔다.
5. 필터·시간대·중복 경기·미분류 라인·재경기·분모 0·timeline 누락을 합성 데이터로 검증한다.
6. 변경 범위 검사 후 `npm run check`, 필요한 DB 검사, 운영 smoke를 실행한다.
