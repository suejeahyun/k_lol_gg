# 대회 밸런스·내전 MMR 점검과 개편안

작성·확인일: 2026-10-29 (Asia/Seoul)

이 문서는 현재 작업 트리의 코드, 회귀 테스트, 합성 입력의 실제 실행 결과를 구분해 기록한다. 운영 회원 기록을 분석하거나 운영 점수를 재계산하지 않았다. 아래 세 가지 오류의 수정 코드는 작업 트리에 있으며, 운영 반영 여부와 최종 전체 검사 결과는 해당 릴리스 QA 문서를 기준으로 확인한다. 새 MMR 산식과 공동 대회 엔진은 아직 구현하지 않았다.

## 1. 선택한 방향

현 엔진의 재현 가능한 계산, 포지션 제약, 수동 배치 검증, 경기 정정·무효화 이력은 유지한다. 선수 교체와 참가 정원, 순위 조회의 명확한 오류부터 수정한다. 점수 정책은 기존 결과를 보존한 상태에서 새 산식을 병렬 계산하고, 시간순 검증 결과를 본 뒤 전환한다.

다음 산식의 기본 방향은 **팀 승패와 상대 강도, 실력 추정의 불확실성**이다. 포지션별 자료가 적으면 개인의 전체 추정치에 가깝게 보정하고, 티어는 신규 선수의 제한된 초기 참고값으로 사용한다. KDA·참여 횟수를 주요 실력 점수에 직접 보상하는 요소는 첫 후보에서 제외한다. 장기 미참여는 감점보다 불확실성을 늘리는 방식으로 처리한다. 이 방향은 설계 결정이며, 실제 가중치·모델의 우수성은 아직 입증되지 않았다.

각 커뮤니티의 기존 MMR을 곧바로 하나의 순위로 합치지 않는다. 같은 60점도 상대 집단과 산식이 다르면 의미가 다르다. 공동 대회는 버전을 고정한 자체 평가 범위와 검증된 계정 연결을 사용하고, 커뮤니티 간 비교는 실제 교류 경기 자료가 쌓인 뒤 검증한다.

## 3. 대회 방식과 팀 배치에서 남은 문제

### 3.1 스위스·랜덤 예선 이름과 실제 동작이 다르다

`src/modules/competitions/destruction/fixtures.ts`의 `buildPreliminaryFixtures`는 조별·전체 라운드로빈을 별도로 처리하고, 나머지 방식은 완성된 라운드로빈의 라운드를 순서대로 반복한다. 따라서 `SWISS_ROUND`는 성적에 따라 다음 상대를 다시 정하는 스위스 운영이 아니며, `RANDOM_ROUNDS`에도 해당 함수의 무작위 대진 생성은 없다.

권고: 새 대회 생성 화면에서 실제 지원 수준을 표시하고, 미구현 방식은 선택을 제한한다. 진행 중인 대회의 저장된 방식·대진은 유지한다. 스위스는 라운드 결과 확정 후 다음 대진 생성, 재대결 회피, 부전승·동률 규칙을 별도 구현한다. 랜덤 방식은 기록된 시드와 재생 가능한 추첨을 구현한 뒤 활성화한다. 이 변경은 현재 패치에 포함하지 않았다.

### 3.2 10명 이벤트와 여러 팀 대회를 분리해야 한다

현재 `eventTeamBalanceParticipants`와 `normalizePlayers`는 정확히 10명의 5:5 배치를 요구한다. 이번 정원 수정은 이 계약을 지키는 수정이다. 이를 여러 커뮤니티가 참가하는 대회에 그대로 사용하면 안 된다.

공동 대회는 참가 팀·팀별 명단·예비 선수·확정 시각·라운드·결과 승인이라는 별도 운영 단위를 둔다. 기존 `competitions/core`의 대진·순위 계산과 10명 팀 배치기는 필요한 단계에서 재사용한다. 공동 대회 등록 인원을 10명으로 제한하는 설계를 선택한 것은 아니다.

### 3.3 추천 점수와 제약을 운영자가 해석할 수 있어야 한다

`src/modules/team-tools/domain/team-balance.ts`는 포지션 선호, 상위 티어 배치, 라인 차이 등 여러 요소를 계산하고 `compareInhousePriority`로 우선순위를 적용한다. 단일 점수만 최소화하는 엔진은 아니다. 자동 후보와 수동 배치가 같은 선수별 점수 계산을 사용하는 구조는 유지할 가치가 있다.

추가할 정보는 새 지표의 수보다 **왜 이 배치를 추천했는지**다. 기존 후보별 비교에 총점·라인 차이·주포지션 배정·자료 부족·완화된 제약을 함께 보여준다. 강제 제약을 만족하지 못한 결과를 정상 최적안처럼 표시하지 않는다. 운영자의 수동 변경에는 사유와 변경 전후 비교를 남긴다.

### 3.4 계산 시간은 별도 측정이 필요하다

이전 focused 검사에서 fallback 검색을 포함한 테스트 한 사례가 약 12.9초 걸렸다는 관찰이 있다. 테스트 전체 소요 시간이므로 운영 요청의 지연 시간으로 단정할 수 없다. 대표적인 10명 입력과 포지션 부족 입력을 분리해 서버의 p50·p95 계산 시간, 후보 수, 메모리를 측정해야 한다.

같은 입력·정책 버전의 계산 재사용, 실행 시간 제한, 백그라운드 작업과 취소를 우선 검토한다. 속도를 높이기 위해 포지션·공정성 제약부터 약화시키지 않는다. 대규모 최적화와 새 알고리즘 추가는 측정 후 결정한다.

## 4. 현재 MMR 산식의 합성 실험

대상: `src/modules/mmr/domain/mmr-projection.ts`, 산식 버전 `V2_DETERMINISTIC_1`. `rebuildMmrProjection`을 현재 코드에서 직접 호출했다. 외부 API와 운영 DB는 사용하지 않았다.

공통 조건은 BLUE·RED 각 5명, 포지션 TOP/JGL/MID/ADC/SUP, 모든 선수 K/D/A=2/2/4, 초기 50점, 수동 보정 없음이다. 이는 산식의 성질을 확인하기 위한 합성 입력이다. 실제 경기에서 같은 KDA가 같은 기여를 뜻한다거나, 운영 회원 전체가 아래와 같은 편향을 겪는다는 결론은 아니다.

### 4.1 입력 묶음에 따라 같은 9승의 점수가 달라진다

| BLUE TOP의 기록 | 최종 점수 | 표본 수 | 현재 `confidence` |
| --- | ---: | ---: | ---: |
| 9승을 한 match/series의 9개 game으로 입력 | 55.47 | 9 | 0.30 |
| 같은 9승을 1개 game씩 9개 match/series로 입력 | 67.56 | 9 | 0.30 |

현재 `applyMatch`는 한 series 내 게임을 모두 이전 프로필로 계산하고, 선수별 게임 변화량의 **평균**을 series가 끝난 뒤 한 번 적용한다. 9개 series에서는 매번 업데이트된 프로필을 사용하므로 갱신 횟수도 달라진다.

이는 특정 표본의 우연이 아니라 입력 단위에 종속된 정책이다. 경기당 실력 추정을 의도한다면 저장 묶음이 점수에 영향을 주지 않도록 실제 게임의 확정 순서로 계산해야 한다. 반대로 rating period를 사용할 경우 기간을 명시적으로 고정해야 하며, 운영자의 문서 묶음 선택으로 달라져서는 안 된다. 기존 산식의 단순 버그 수정으로 점수를 소급 변경하지 않고 다음 버전의 핵심 변경으로 다룬다.

### 4.2 같은 승패·KDA에도 포지션별 누적 방향이 다르다

한 series에서 BLUE가 1승 1패했을 때의 결과다. 이벤트 변화량은 평균 적용 전 개별 게임 값이다.

| 포지션 | 승리 이벤트 변화량 | 패배 이벤트 변화량 | 최종 점수 |
| --- | ---: | ---: | ---: |
| TOP | +5.47 | −4.53 | 50.47 |
| JGL | +6.00 | −3.96 | 51.02 |
| MID | +6.00 | −3.96 | 51.02 |
| ADC | +5.86 | −4.24 | 50.81 |
| SUP | +5.20 | −4.70 | 50.25 |

`performanceScoreBp`는 KDA·사망·서포터 어시스트 보너스를 더한 값 전체에 포지션 배율을 곱한다. 그 값은 공통 기준 5,000과 비교되어 변화량에 반영된다. 따라서 포지션 배율이 단순한 표현상의 차이를 넘어 기본 상승·하락 방향에 영향을 준다.

포지션마다 동등한 예상 성과에서 장기 평균이 어떻게 움직이는지 검증해야 한다. 다음 산식의 첫 후보는 승패 기반으로 두고, 개인 지표는 충분한 검증을 거친 보조 분석에 사용한다. KDA를 지키는 플레이가 승리에 대한 기여보다 점수상 유리해지는 유인도 함께 검토한다.

### 4.3 현재 신뢰도는 표본 충족도다

계산식은 `min(1, round(sampleSize / 30, 4))`에 해당한다.

| 경기 수 | 값 |
| ---: | ---: |
| 1 | 0.0333 |
| 5 | 0.1667 |
| 30 | 1.0000 |
| 60 | 1.0000 |

30경기를 채우면 100%가 되지만, 상대 다양성·최근성·예측 오차·통계적 구간은 평가하지 않는다. 따라서 화면에서 “신뢰도 100%”를 예측 정확도나 실력 확정으로 해석하게 해서는 안 된다. 현재 값을 “표본 충족도”로 설명하고, 실제 불확실성은 다음 산식의 별도 값으로 설계한다. 이번 패치에서 공개 MMR 순위와 관리자 플레이어 목록을 “종합 표본 충족도”로 변경하고 30경기 기준 설명을 추가했다. 데이터 필드와 산식은 유지한다.

### 4.4 오래된 기록의 불확실성이 커지지 않는다

동일한 5경기 승리 series의 `orderKey` 날짜를 2020-01-01과 2026-01-01로 바꾸어 각각 재생해도 TOP은 55.47점, 표본 5, 충족도 0.1667로 동일했다. 현재 함수는 날짜를 정렬에 사용하며 현재 시점과의 차이를 입력받지 않는다.

복귀 선수를 일괄 감점할 근거는 없다. 대신 마지막 유효 경기 이후 기간에 따라 추정 범위를 넓히고, 새 경기로 다시 좁히는 방식을 비교한다. 과거 자료 삭제와 실력 하락 확정을 혼동하지 않는다.

## 5. 팀 밸런스에 입력되는 점수도 함께 개편해야 한다

현재 V1 자료 경로의 `v1BaseScore`는 최고 티어 60% + 현재 티어 30% + 내전 지표 10%다. 내전 지표는 승률 50% + 경기 수 30% + MVP 비율 20%로 구성된다. 여기에 포지션 선호 감점, 최근 솔로 성과, 포지션 경험, MMR 보정, 운영자 보정 등이 더해진다. 이 비율은 해당 V1 경로에 대한 설명이며 모든 입력 경로가 이 공식을 쓰는 것은 아니다.

확인된 설계 과제는 다음과 같다.

| 항목 | 우려되는 효과 | 선택한 개선 방향 |
| --- | --- | --- |
| 과거 최고 티어 60% | 과거 시점·경과 기간을 충분히 설명하지 못하고 현재 자료보다 오래 영향을 줌 | 티어는 출처·시점을 가진 제한적 초기 참고값으로 사용. 내전 자료가 쌓이면 영향 축소 |
| 경기 수를 점수에 가산 | 활동량과 실력이 섞임 | 경기 수는 추정의 불확실성을 줄이는 자료로 사용 |
| MVP 비율 | 선발 방식과 표본에 좌우됨 | 투표/선정 출처를 기록하고, 본점수 반영은 검증 전 확대하지 않음 |
| KDA·피해량·시야 절대 기준 | 역할·챔피언·경기 길이·패치의 차이를 혼합할 수 있음 | 주 산식에서 제외한 후보와 비교. 쓰더라도 맥락 보정과 시간순 검증 선행 |
| 여러 곳의 포지션 가중·감점 | 같은 정보가 중복 반영될 가능성 | 구성요소별 기여를 보이며 제거 실험으로 실제 효용 확인 |
| 운영자 보정 | 이유·유효기간이 없으면 개인 판단이 영구 점수화됨 | 사유·범위·만료·작성자 감사 기록을 유지/보강하고 대회별 적용 범위 고정 |
| 커뮤니티별 독립 MMR | 점수 스케일과 상대 집단이 다름 | 공동 대회용 별도 평가 범위. 원본 커뮤니티 점수를 무조건 덮어쓰지 않음 |

위 항목은 운영 데이터로 성능 저하를 입증한 버그 목록이 아니다. 현재 산식의 구조에서 도출한 검증 대상이며, 가중치를 임의로 바꾸는 것으로 해결 완료를 선언하지 않는다.

## 7. 새 산식의 구현·검증 순서

1. **평가 계약 확정:** 게임 단위 순서, 동일 시각 처리, 정정·무효화, 신규/복귀 선수, 포지션 이동, 팀 변경, 수동 보정의 의미를 문서와 고정 입력으로 정의한다.
2. **비공개 병렬 계산:** 현재 산식을 기준선으로 보존하고 승패·상대 강도·불확실성 후보를 별도 버전/세대로 계산한다. 화면 순위와 대회 배치는 기존 값을 유지한다. 신규 모델 구현의 라이선스도 선택 시 확인한다.
3. **시간순 평가:** 과거 구간으로 조정하고 그 이후 구간으로 검증한다. 한 게임의 결과나 미래 티어·미래 집계가 그 게임의 입력에 섞이지 않도록 당시 스냅샷을 사용한다. 동일 series와 반복 참가 집단의 의존성도 반영한다.
4. **성능·공정성 비교:** Brier score·log loss·승률 구간별 실제 승률을 기준선과 비교한다. 포지션, 신규/기존, 복귀, 커뮤니티별로 나누어 과대·과소 평가를 확인한다. 작은 표본은 결론 유보와 구간을 함께 표시한다.
5. **운영 미리보기:** 선수별 변화량, 순위 변화, 팀 추천 변화, 정정·무효화 재생 결과를 비교한다. 대회 진행 중에는 기존 버전을 고정한다. 불리한 집단이나 큰 급변이 생기면 원인을 설명하기 전 전환하지 않는다.
6. **전환과 복구:** 새 대회부터 검증된 버전을 선택하고, 원본 경기와 이전 projection을 보존한다. 문제가 생기면 이전 버전의 projection을 다시 활성화한다. 운영 점수의 일괄 전환은 별도 실행 기록과 검증 결과를 남긴다.

TrueSkill 계열은 팀 결과와 실력 평균·불확실성을 함께 다루므로 우선 비교 후보로 적합하다. 이 문서의 선택은 구조적 적합성에 관한 판단이며 이 서비스에서의 우수성을 입증한 결과는 아니다. Glicko-2의 rating deviation·비활동 처리도 비교 기준으로 참고하되, 개인 간 대결을 설명하는 원식을 5인 팀에 단순 이식하지 않는다. [Microsoft TrueSkill 설명](https://www.microsoft.com/en-us/research/project/trueskill-ranking-system/), [Glickman의 Glicko-2 원문](https://www.glicko.net/glicko/glicko2.pdf)

수치상 통과 기준은 표본 크기와 현재 기준선 측정 후 고정한다. 결과를 본 다음 유리한 기준을 골라 통과시키지 않는다. 실제 자료가 부족하면 신규 모델은 계속 비공개 비교 상태로 둔다.

## 8. 외부 연동과 공개 범위의 확인 사항

Riot 일반 정책은 공식 랭킹의 대체 시스템과 MMR/ELO 계산기를 금지 대상으로 명시하고, 제품의 새 기능·변경 검토 및 제품별 운영 키 사용을 요구한다. 따라서 자체 내전 평가라는 설명만으로 허용을 단정하지 않는다. 기존 신청·승인 범위에서 팀 배치와 평가 표시가 어떻게 다뤄졌는지 확인하고, 새 중앙 제품과 공개 범위는 그 근거에 맞춰 진행한다. 이름을 “내전 점수”로 바꾸는 것만으로 승인 요건을 충족한 것으로 취급하지 않는다. [Riot 일반 정책](https://developer.riotgames.com/policies/general) (2026-10-29 확인)

커뮤니티 연동을 이유로 닉네임이나 추정만으로 동일 인물을 합치거나 “위험 점수”를 자동 생성하지 않는다. 검증된 계정 연결과 권한이 있는 운영 기록만 별도 공유 정책으로 다룬다. 실력 점수는 운영상 제재 판단의 근거로 사용하지 않는다.

## 9. 재현 안내와 완료 기준

합성 실험은 `rebuildMmrProjection({ generation: 1, matches })`에 아래 조건으로 입력하면 재현된다.

- 참가자 ID는 `BLUE-TOP` 등 팀·포지션 조합 10개로 고정한다. 모든 참가자는 `kills: 2, deaths: 2, assists: 4`를 사용한다.
- 각 game은 고유 ID·gameNumber, 각 match는 고유 ID·orderKey와 `status: PUBLISHED`를 사용한다.
- 1승1패는 한 match에 winnerTeam이 BLUE·RED인 두 game을 넣는다.
- 9승 비교는 동일한 BLUE 승리 game 9개를 한 match에 넣거나, 동일 순서의 9개 match에 각각 하나씩 넣는다.
- 비활동 비교는 동일한 5개 game의 match에서 orderKey 날짜만 바꾼다.
- 결과의 `overallScoreBp / 100`, `sampleSize`, `confidenceBp / 10_000` 및 `matchEvents[].overallDeltaBp / 100`을 비교한다.

이번 오류 수정의 완료 기준은 관련 회귀 검사와 전체 검사, 격리 DB 검사 통과다. 산식 개편의 완료 기준은 별도 버전 구현, 시간순 성능 검증, 운영 미리보기, 되돌릴 수 있는 전환 근거다. 공동 대회의 완료 기준은 여러 커뮤니티의 참가 승인부터 명단 고정·경기 진행·결과 승인·정정까지 실제 흐름이 연결되는 것이다. 이 세 범위를 서로의 완료 근거로 대신하지 않는다.
