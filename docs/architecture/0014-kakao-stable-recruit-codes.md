# ADR 0014: 파티 모집의 고정 코드와 별도 명단 버전

- 결정일: 2026-10-14 KST
- 상태: **사용자 승인에 따른 구현 결정. 통합 검증·운영 배포·휴대폰 설치 상태는 [이번 QA 기록](../qa-evidence/stable-recruit-codes-2026-10-14/README.md)에서 별도로 판정한다.**
- 승인 근거: 사용자가 “처음 한번만 코드를 발급하여 그게 쫑이 되거나 수정되거나” 하는 방식을 먼저 분석하도록 요청했고, 고정 모집코드와 자동 명단 버전을 분리하는 분석을 확인한 뒤 “진행해줘”라고 승인했다.
- 범위: 카카오 `PARTY` 모집의 식별·복사 원본·코드 지정 명령. 내전 `INHOUSE`의 코드·회원 연결·편집 규칙은 변경하지 않는다.
- 선행 결정: [ADR 0010](./0010-kakao-site-linked-copy-forms.md)의 파티 상태별 양식코드 식별과 [ADR 0011](./0011-kakao-party-editable-copy-flow.md)의 파티 코드 표시·운영일 대상 해석만 이 결정으로 대체한다. 선행 문서는 당시 기록으로 보존하며 편집·충돌 병합 정책은 계속 적용한다.

## 배경

기존 모집번호는 유지되지만 `양식코드`는 복사 당시 원본 상태를 식별한다. 같은 상태를 다시 조회하면 재사용하고, 명단이 달라지면 다른 코드가 발급된다. 사용자가 모집의 동일성과 복사 원본의 버전을 같은 코드로 이해하기 쉬웠다.

모집코드만 고정하고 원본 식별을 없애면 예전 양식의 빈칸을 삭제 의도로 볼지, 그 뒤에 참가한 사람을 유지할지 판단할 수 없다. 카카오의 일반 텍스트 메시지에는 사용자가 복사한 시점을 서버만의 숨은 버전으로 전달할 방법도 없다. 따라서 모집 식별과 원본 버전을 함께 전송하되 각각 다른 의미로 표시한다.

## 결정 1: 실제 파티 한 건에 코드를 한 번 발급한다

```text
[파티 #3] 5인 파티 · 0/5명
모집코드: ABCDE-23456
명단버전: 1
──────────────
시작 시간 :
게임 종류 :

1.
2.
3.
4.
5.

예비 1.
```

- `모집코드`는 인증된 installation의 논리 scope와 실제 파티 UUID에 영구적으로 연결한다. 물리적인 카카오 방 이름·모집번호·날짜만으로 연결하지 않는다.
- 처음 생성·최초 코드 제공 시 발급한 코드는 참가, 취소, 시간·게임 수정, 날짜 경계 이후에도 동일하다. 이미 존재하던 파티는 새 상세 조회 또는 다음 저장 시 고정 코드를 처음 얻는다.
- 마감·취소·리셋된 파티의 코드는 다른 파티에 재할당하지 않는다. 이전 코드나 복사본으로 종료된 파티를 다시 활성화하지 않는다.
- 새 파티를 만들면 새로운 코드가 생긴다. 사람별·방별로 하나의 코드를 계속 돌려 쓰는 기능이 아니다.
- 정원이 차거나 명단이 비었다는 이유만으로 새 코드나 새 모집을 만들지 않는다. 기존 DRAFT 활성화·마감 정책을 유지한다.

## 결정 2: 명단 버전은 원본을 식별하고 별도로 만료된다

`명단버전`은 사용자 입력 항목이 아니다. 봇이 표시한 모집코드와 버전을 함께 복사한다. 내부 전달에서는 `CODE@version`을 사용하고 사용자 양식에서는 두 줄로 나눈다.

- 같은 코드·운영일·원본 상태를 다시 제공하면 기존 버전을 재사용한다. 원본이 바뀌거나 새로운 운영일의 원본이 필요하면 증가한 버전을 발급한다.
- 버전은 원본 레코드의 식별자다. 파티 aggregate revision과 같은 값이라는 보장은 하지 않는다.
- 원본은 발급 운영일 다음 날 **06:00 KST**에 만료된다. 자정 경계는 아니다. 영구 모집코드와 명단 원본의 유효기간을 구분한다.
- 원본이 만료되면 같은 코드의 최신 양식을 다시 받도록 안내한다. 오래된 버전으로 새 원본을 대신 조회하거나 코드 없는 양식으로 낮춰 저장하지 않는다.
- 만료 원본을 정리해도 코드와 마지막 버전 번호는 보존한다. 이미 발급된 `CODE@version`은 다시 사용하지 않는다.
- 전체 복사 저장은 기존 원본·현재 명단·제출값의 세 방향 비교를 유지한다. 다른 참가자의 새 이름 보존, 서로 다른 항목의 병합, 같은 항목의 충돌 거부, 중복 이름·정원·빠진 번호 행 검증을 계속 적용한다.
- 번호형 `PARTY_NUMBER`의 이름·시간·게임 편집과 라인형 파티의 기존 제한은 그대로다. 코드 변경으로 모든 파티 종류의 편집 권한을 확장하지 않는다.

모집 자체의 수명도 별개다. 기존 자동 마감 작업의 비활동 기준과 이전 운영일 DRAFT 정리는 유지한다. 고정 코드가 있다는 이유로 이미 종료된 모집을 살리거나 자동 마감 대상에서 제외하지 않는다.

## 결정 3: 코드 지정 명령은 날짜와 무관하게 같은 UUID를 선택한다

| 입력 | 대상과 동작 |
| --- | --- |
| `구인상세 ABCDE-23456` / `상세 ABCDE-23456` | 코드가 가리키는 진행 중 모집의 최신 양식 |
| `상세 ABCDE-23456 추가 이름` | 해당 모집의 현재 명단에 한 명 추가 |
| `상세 ABCDE-23456 삭제 이름` | 해당 모집의 현재 명단에서 명시적으로 한 명 삭제 |
| `구인마감 ABCDE-23456` / `구인쫑 ABCDE-23456` / `구인종료 ABCDE-23456` / `ABCDE-23456ㅉ` | 해당 모집을 마감. DRAFT면 초안 취소 |
| `상세 3` / `상세 3 추가 이름` / `상세 3 삭제 이름` / `3ㅉ` | 기존처럼 현재 운영일의 번호 3을 대상 지정 |

코드 명령은 기존 `PARTY_DETAIL`, `PARTY_MEMBER_ADD`, `PARTY_MEMBER_REMOVE`, `PARTY_FINISH` 분류를 사용하고 canonical `BY_CODE`로 전달한다. dispatcher는 인증된 scope 안에서 UUID·실제 모집일·번호·상태를 조회한 뒤 기존 액션에 서버 내부 `partyId`를 넘긴다. 복사 양식의 번호가 코드 대상의 실제 번호와 다르면 저장하지 않는다.

운영일 이후 같은 번호로 다른 파티가 생겨도 코드 지정 수정·마감은 원래 UUID를 대상으로 한다. 최신 양식과 충돌 응답 역시 그 UUID로 다시 조회하며 오늘의 같은 번호로 바꾸지 않는다. 코드 조회가 실패했을 때 번호 기반 경로로 재시도하지 않는다.

## 결정 4: 코드는 인증 수단이 아니다

기존 HMAC 서명, 정적 RECRUIT 프로필, installation scope, 서명 nonce/event 멱등성, transaction 안의 권한·대상 상태·잠금 검증을 유지한다. 코드를 알거나 양식을 복사한 사실만으로 다른 scope의 파티를 조회·수정할 수 없다. `partyId`는 서버가 코드로 해석한 내부 값이며 텍스트에서 직접 받아 권한을 부여하지 않는다.

코드 조회는 scope 해시와 파티의 실제 `sourceRoomId`를 모두 확인한다. 저장 시에도 원본의 코드·버전·scope·UUID·운영일·유효기간을 검증하고 현재 잠긴 파티에 대해 수정 가능 상태를 다시 확인한다. 종료된 코드 요청은 변경 없이 종료 사실을 안내한다.

## 결정 5: 기존 형식과 내전은 호환한다

- 기존 `양식코드: CODE`는 기존 원본 테이블·유효기간·편집 검증 경로로 지원한다. 새 양식과 구형 코드 줄을 섞거나 새 코드/버전 중 한 줄만 제출하면 저장하지 않는다.
- 전환 전에 받은 legacy 양식은 해당 운영일 유효기간 안에서 계속 처리한다. 운영의 기존 snapshot을 backfill하거나 기존 code를 새 registry에 재할당하지 않는다.
- 긴 저장기준이나 코드 없는 구형 양식의 기존 보존 제약은 유지한다.
- 내전은 기존 `양식코드` 방식과 ADR 0012의 회원·사이트 신청 보호 규칙을 유지한다.
- 기존 휴대폰의 compact copy 전달은 새 두 줄을 포함한 전체 텍스트를 전달할 수 있다. 서버 양식의 변경만으로 설치 확인을 새로 주장하지 않는다.
- 코드를 직접 입력하는 새 명령은 휴대폰 **R28**의 사전 전달 핸들러가 필요하다. 공개 생성·비공개 설치본 생성·실기기 교체는 각각 기록한다.

## 저장·migration·복구

`0049_stable-recruit-codes`는 Drizzle 스키마를 원본으로 두 테이블을 추가한다. 기존 테이블·열·데이터를 삭제하거나 기존 양식 원본을 이동하지 않는다.

| 테이블 | 책임 |
| --- | --- |
| `recruiting.kakao_recruit_codes` | 전역 고유 code, scope 해시+UUID 고유 연결, 마지막 발급 버전, 생성 시각 보존 |
| `recruiting.kakao_recruit_form_snapshots` | `(code, version)` 원본, 운영일, 상태 해시·JSON, 만료 시각. registry FK는 삭제 제한 |

처음 파티를 만들 때 같은 transaction에서 파티 행 저장보다 먼저 코드를 발급하므로 registry→파티의 즉시 FK는 두지 않는다. 발급자는 권한을 확인한 파티 UUID만 사용하고 전체 transaction 실패 시 코드 발급도 rollback한다. 원본→registry FK, 코드/scope/버전/JSON 크기/만료 제약은 DB에서 강제한다.

기존 registry 행을 잠가 동시 발급을 직렬화한다. 최초 발급의 고유 제약 경합과 우연한 코드 충돌은 기존 대상 소유권을 바꾸지 않고 재조회·재시도한다. 정리 작업은 한 번에 최대 256개의 만료 원본만 삭제하고 영구 registry와 버전 번호는 지우지 않는다. 무트래픽 중 물리 삭제를 보장하는 새 scheduler는 이 변경에 포함하지 않는다.

배포 전 fresh·기존 자료가 있는 upgrade·재실행 no-op·구 writer 호환을 격리 PostgreSQL에서 확인한다. 운영 적용은 새 백업·복원 검증과 reviewed migration rehearsal을 거친 뒤 진행하며 근거는 QA 기록에 남긴다. 문제가 생기면 이전 앱으로 되돌리고 추가 테이블은 보존한다. 이전 앱은 새 코드 형식을 이해하지 못할 수 있으므로 rollback 중에는 당시 서버에서 상세 양식을 다시 받아야 한다. 즉석 down migration이나 운영 테이블 삭제로 복구하지 않는다.
