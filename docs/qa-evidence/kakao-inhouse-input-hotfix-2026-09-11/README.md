# 긴급 내전 신청 HTTP 400 입력 핫픽스 QA 근거

- 검증일: 2026-09-11
- 대상: 협곡 내전 참가 신청 양식 파싱과 V1 strict 휴대폰 설치 후보 R5
- 소스 상태: 현재 작업 트리에만 반영
- 커밋·푸시·운영 배포: 미진행
- 실제 휴대폰 MessengerBot R 컴파일: 미확인
- 실제 카카오방 E2E: 미확인

## 판정 요약

### 확인됨

- 기존 파서는 협곡 내전 참가자 행을 `/`로 나눈 뒤 네 번째 필드 전체를 주라인으로 읽었다.
- 실제 입력 `2.김동휘/M/M/Mid all`에는 주라인과 부라인 사이 `/`가 없어 기존 파서가 `mainPosition="Mid all"`로 해석했다. 이 값은 허용 포지션이 아니어서 `INVALID_FORM`, HTTP 400으로 종료됐다.
- 전용 내전 참가자 행 파서가 추가됐다. `1.지오/G/E/AD/Mid`는 `mainPosition=ADC`, `subPositions=[MID]`로 처리한다.
- 제한된 누락 구분자 입력 `2.김동휘/M/M/Mid all`은 `mainPosition=MID`, `subPositions=[]`로 복구하며 `RECOVERED_MISSING_POSITION_DELIMITER` 진단을 남긴다.
- 누락 구분자 복구는 마지막 필드가 공백으로 나뉜 정확히 두 개의 유효 포지션 별칭일 때만 적용한다. `Mid all extra`처럼 범위를 벗어나면 거절한다.
- 참가자 3~10번의 빈 행은 정상적인 빈 슬롯으로 허용한다. 전각 숫자·구두점과 카카오 이스케이프가 포함된 번호 행도 기존 입력 내결함성 범위에서 처리한다.
- `없음`, `-`, `미정`은 부라인 필드에서만 빈 부라인으로 처리한다. 주라인에 사용하면 거절한다.
- `아무데나`처럼 정의되지 않은 포지션 토큰은 자동 추정하지 않고 거절한다.
- V1의 화면 문구·출력·사용 순서는 바꾸지 않았고, 휴대폰에서 서버로 보내는 요청은 기존 단일 HTTP·5초 제한을 유지한다.
- 제공된 전체 검증에서 `npm run check`는 exit 0이었다.

### 추가 확인 필요

- R5 변경은 아직 커밋하거나 원격 저장소에 푸시하지 않았다.
- R5 서버 코드는 운영에 배포하지 않았다.
- R5 설치본을 실제 휴대폰에 복사하고 MessengerBot R에서 컴파일하지 않았다.
- 실제 카카오방에서 문제 입력을 보내 접수 완료 응답과 서버 저장 결과를 확인하지 않았다.
- 배포 후 `INVALID_FORM` 감소 폭과 복구 진단 발생량은 아직 측정하지 않았다.

## 문제와 영향

### 발견한 문제와 근거

협곡 참가 양식의 안내 구조는 `이름/현티어/최고티어/주라인/부라인`이다. 기존 구현은 `/` 기준으로 나눈 네 번째 값을 주라인으로 사용했다. 실제 제보 입력은 다음과 같다.

```text
1.지오/G/E/AD/Mid
2.김동휘/M/M/Mid all
3.
4.
5.
6.
7.
8.
9.
10.
```

두 번째 행은 `Mid`와 `all` 사이 구분자가 공백으로 바뀌었다. 기존 구현은 이를 하나의 주라인 문자열 `Mid all`로 보아 양식 전체를 `INVALID_FORM`으로 처리했다. 공개 HTTP 결과는 400이었다.

### 사용자 및 운영 영향

- 사용자는 화면상 어느 필드가 잘못됐는지 알기 어려운 일반 양식 오류를 받았다.
- 참가자 한 명의 구분자 누락 때문에 비어 있는 3~10번을 포함한 전체 내전 신청이 저장되지 않았다.
- 같은 양식을 다시 보내도 원인을 고치지 않으면 반복해서 HTTP 400이 발생할 수 있었다.
- 운영자는 정상 신청 의도가 있는 입력과 실제 미지정 포지션을 구분하기 어려웠다.

## 해결 방법과 안전 경계

| 입력 | 판정 | 저장 의미 |
|---|---|---|
| `1.지오/G/E/AD/Mid` | 허용 | 주라인 `ADC`, 부라인 `[MID]` |
| `2.김동휘/M/M/Mid all` | 제한 복구 | 주라인 `MID`, 부라인 `[]` |
| `3.` ~ `10.` | 허용 | 빈 슬롯, 참가자 미생성 |
| `2.김동휘/M/M/AD/없음` | 허용 | 주라인 `ADC`, 부라인 `[]` |
| `2.김동휘/M/M/없음/MID` | 거절 | 주라인 미지정 토큰 |
| `2.김동휘/M/M/AD/아무데나` | 거절 | 부라인 미지정 토큰 |
| `2.김동휘/M/M/Mid all extra` | 거절 | 제한 복구 범위 초과 |

허용하지 않은 값을 임의의 포지션으로 바꾸는 정책은 추가하지 않았다. 이번 복구는 실제 실패 입력처럼 공백으로 합쳐진 두 개의 유효 포지션 별칭에만 적용한다.

## KPI

개인정보와 신청 원문을 저장하지 않고 결과 코드와 집계값만 사용한다.

- 내전 snapshot 요청 중 `INVALID_FORM`·HTTP 400 비율
- `RECOVERED_MISSING_POSITION_DELIMITER` 발생 건수와 이후 접수 성공률
- 내전 신청 양식 재전송률
- 미지정 포지션 토큰 거절 건수
- 카카오 요청 성공률, timeout 비율, 처리시간 p50·p95
- 실제 저장된 참가자 수와 사용자에게 표시된 참가자 수 불일치 건수

현재 운영 기준선이 없으므로 목표 수치는 임의로 만들지 않았다. 배포 전후 같은 기간을 비교하고, 잘못된 포지션 저장과 표시·저장 불일치는 0건을 기준으로 본다.

## 배포 전 테스트와 롤백

1. 현재 검증 결과와 R5 두 SHA-256을 릴리스 근거에 연결한다.
2. 서버 변경을 커밋·푸시한 뒤 배포 ID와 대상 commit을 확인한다.
3. 운영 `/api/health`와 실제 문제 입력의 서버 응답을 확인한다.
4. 휴대폰에 정확한 R5 설치본을 복사하고 MessengerBot R에서 컴파일한다.
5. `/봇버전`으로 R5를 확인한 뒤 실제 카카오방에서 정상 입력, `Mid all`, 미지정 토큰 거절을 확인한다.

이번 변경에는 DB migration이나 데이터 일괄 변경이 없다. 배포 뒤 문제가 생기면 서버는 직전 확인된 R4 서버 릴리스로 되돌리고, 휴대폰은 직전 확인된 설치본으로 교체한다. 이미 접수된 신청·receipt를 삭제하지 않고 동일 fixture와 실카카오 smoke를 다시 실행한다.
