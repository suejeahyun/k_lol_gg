# 별도 재검토 — 서비스 후속 수정 1.0.2

검토일: 2026-10-06 KST. 기준 HEAD `bae10999510f591ea827827bb44ef2cdcc9268f0` 이후 통합 diff를 읽었다. 검토자는 이번 접수 API·scope 검사·신청 문구 변경을 구현하지 않았으며 소스 수정 없이 재검토했다. 외부 운영 점검은 별도 [실행 증거](../service-followup-2026-10-06/external-runtime.md)에 연결한다.

## 발견 사항과 판정

현재 변경 diff와 아래 검사 범위에서 새로 수정해야 할 중대 코드 오류나 명확한 과업 방해 요소는 발견하지 못했다. 앞서 재현된 정상 접수 코드의 내부 scope 예외는 원인과 수정이 일치한다. 다만 **운영 MMR 공식 전환 대기와 미소비 변경 이벤트 13건은 해결 완료로 판정하지 않는다.** 이는 이 접수 API 패치와 다른 운영 과업이며 별도 분석·실행 근거가 필요하다.

| 검토 대상 | 소스·검사에서 확인한 내용 | 판정 |
| --- | --- | --- |
| 소유자 접수 수정·취소·이미지·카카오 연결 | 정식 공개 코드는 기존 `MR2`+대문자 16진 16자리 계약을 사용한다. 내부 scope를 만들 때만 소문자로 바꾸며 서비스의 조회/대상 코드는 원래 대문자로 보존한다 | 정상 발급 코드가 lower-case scope 검증에서 예외를 내던 공통 원인을 해결. 코드를 임의로 대소문자 무시 조회하는 정책 변경이 아님 |

| 잘못된 주소·오류 응답 | 접수 mutation의 잘못된 코드는 해시 계산 전에 404. 관리자 등의 동적 scope가 문자/길이 규칙을 벗어나면 `mutationHeaderGuard`가 JSON/이미지 공통으로 구조화된 400 `INVALID_INPUT` 반환 | 예외를 200으로 숨기지 않고 입력 오류로 복구 가능. `no-store` 응답 유지. trace ID·서비스 오류 응답 경계 유지 |
| scope 충돌 | 허용 코드 집합이 대문자 16진으로 고정되어 소문자 변환은 이 집합에서 일대일이다. 코드·update/cancel/images·카카오 create/revoke 구분자가 유지됨 | 서로 다른 접수나 작업을 같은 scope로 합치지 않음. 단위 회귀에서 같은 코드/작업의 재생과 다른 코드·create/revoke의 다른 해시 재료를 확인 |
| 기존 해시·영수증 | 공통 hash domain·구분 문자·키 검증은 그대로이고 기존 regex를 공유 validator로 추출했다. 정상 lower-case scope의 해시 재료는 동일. repository receipt는 actor+scope+key와 요청 해시를 검사하고 transaction의 세션 확인 후에만 재생 | 기존 정상 관리자/생성 요청의 영수증을 무효화하지 않음. 종전 대문자 owner scope는 해시 생성 전에 실패했으므로 그 경로의 성공 receipt를 다른 해시로 이관할 문제를 확인하지 못함 |
| 이미지 업로드 | scope 문자열 외에 소유권·길이·형식·해시·게임 번호·작업 제한·예약/완료/보상 삭제 경계 변경 없음 | 실패 이미지의 revision 보존, 정상 업로드/재생, 종결 접수의 추가 업로드 거부를 실제 격리 HTTP에서 확인 |
| 성공·복구 응답 | `matchMutationResponse`와 ETag, `Idempotency-Replayed`, 저장소 receipt 구현 변경 없음 | 실제 HTTP 재생에서 같은 결과/헤더, 동시 수정 200+412, 새 revision으로 복구가 통과 |
| 신청 취소 뒤 다시 참가 | CANCELLED에 ‘다시 참가 신청’, 검토 완료/마감에 ‘신청 상태’, 재신청 성공에 접수 문구를 적용 | 상태를 잘못 ‘수정’으로 설명하던 부분만 수정. 신청/정원/예비/검토/권한 처리 분기는 바꾸지 않음 |

공통 scope validator는 malformed scope를 해시 함수 밖에서 검사하도록 연결한 것으로, regex가 허용하는 정상 요청의 범위를 확대하지 않는다. 잘못된 입력의 오류 우선순위가 구조화된 400/404로 달라진 것은 수정의 목적과 일치한다.

## 실제 근거와 검증 경계

- [수정 전 HTTP 실패](../2026-10-06-owner-task-http/before-diagnostics.log)에서 정상 소유자 동시 수정이 기대한 200/412 대신 500/500으로 실패한 기록을 읽었다. 테스트 기대값을 느슨하게 바꾸어 통과시킨 수정이 아니다.
- [수정 후 격리 HTTP·계약](../2026-10-06-owner-task-http/http-and-contracts.log)에서 생성/재생 → 소유자 조회 → 동시 수정 → 최신 revision 복구 → 잘못된 이미지 복구 → 업로드/재생 → 취소/재생 → 종결 변경 거부, 새 접수 → 저장한 팀 출처 → 두 이미지 → 거절 사유 → 재개 → 검토/승인/재생 → 공개 경기까지 통과했다. 타인·미승인·익명·폐기 세션 차단도 포함한다.
- 같은 HTTP 기록에서 팀 생성/재생, 타인 읽기/쓰기 거부, 동시 저장 200/412, 재계산/재생 및 최신 상태 재저장을 확인했다. 운영 실제 회원/경기 시험이 아니라 임시 PostgreSQL과 합성 계정·이미지·storage/OCR adapter를 사용했다.
- 독립 검토자가 현재 소스의 `npx --no-install tsx --test tests/match-mutation-scope.test.ts`를 실행해 2/2 PASS, exit 0을 확인했다. 실제 카카오 owner route/공통 HTTP 소스를 컴파일해 handler를 실행하고 기존 hash 함수를 사용한다. 카카오 공급자의 실제 메시지 전송이나 원격 사진 수신을 시험하는 테스트는 아니다.
- [최종 필수 검사](check.log)는 계약 463 PASS, 단위 1,047 PASS+조건부 skip 1, lint 오류 0/기존 경고 58, 타입·ERD·이미지·production build 완료 기록을 확인했다. 운영 배포 성공과는 별개다.
- 신청 취소의 실제 브라우저 성공과 수정 전 접수/이어하기 흐름은 [릴리스 본문](README.md)에 연결되어 있다. 브라우저 원본 조작은 통합 담당자가 수행했으며 독립 검토자가 다시 수행했다고 주장하지 않는다. 수정 후 최종 브라우저·배포/운영 결과는 해당 후속 기록을 따른다.

## 작업 공간·범위

이 후속 작업을 시작할 때 해당 worktree는 `bae10999`에서 clean이었다. 검토 시 tracked 변경은 소유자 접수 route 4개, match HTTP/shared idempotency 2개, 신청 action 문구 1개, 격리 HTTP harness 1개였고 모두 통합 담당/지정 담당자의 작업과 일치했다. 신규 scope 회귀와 QA/패치 문서도 요청 범위였다. 무관한 패키지·스키마·migration·정책·자산 변경은 관측하지 못했다. 사용자의 다른 checkout이 clean하다고 일반화하지 않으며 이번 검토에서 그 파일을 수정하지 않았다.

## 남은 운영·외부 조건

운영 Blob의 실제 업로드·내용검사·삭제·부재 확인과 Riot 운영 status-v4 수락은 [별도 실제 증거](../service-followup-2026-10-06/external-runtime.md)에서 통과했다. 그 결과도 합성 owner HTTP의 모든 경로를 운영 쓰기로 검증했다는 의미는 아니다. 해당 증거가 새로 확인한 MMR 전환 대기, Riot 최근 24시간 PARTIAL 18건의 개별 원인, RSO 자격/실동의, 카카오 실기기 수신·타이머·재등록, 외부 경보 수신·PITR·기기 접근성은 구분해 남긴다.

이 변경 범위에서는 동일 기능을 새로 구현하거나 hash/receipt 형식을 교체할 근거가 없다. 기존 권한과 업무 흐름을 유지한 수정은 적절하며, 알려진 별도 운영 미완결 항목까지 포함해 서비스 전체가 완료됐다는 근거로 이 소스 리뷰를 사용하지 않는다.
