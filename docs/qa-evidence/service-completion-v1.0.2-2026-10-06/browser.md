# 수정 후 실제 브라우저·화면 검증

2026-10-06 KST, `npm run check`를 통과한 optimized Next 빌드와 안전 가드가 적용된 임시 PostgreSQL 18 fixture를 사용했다. CUA의 실제 페이지 조작이며 운영 회원 데이터는 변경하지 않았다.

| 과업 | 관측 |
|---|---|
| 로그인 후 접수 생성 | 원래 `/matches/submit`로 돌아와 합성 제목·주최자·날짜로 생성, 발급된 코드 URL과 이미지 입력 표시 |
| 수정 저장 | 제목 변경 후 ‘접수 정보를 수정했습니다.’와 변경한 제목 표시. 수정 전 동일 과업의 일반 오류와 비교해 해결 확인 |
| 파일 선택·첫 이미지 등록 | 실제 file chooser에서 합성 PNG 선택, 입력 잠금·처리 안내 뒤 1/2 등록 및 해당 입력 제거 |
| 중복 이미지 오류 | 같은 이미지를 두 번째 게임에 선택하면 오류 안내, 진행률 1/2 유지, 두 번째 입력 재활성 |
| 오류 후 정상 파일 복구 | 다른 합성 PNG를 다시 선택, 2/2 등록·‘검토 대기’ 전환·파일 입력 제거·내 제출 기록 연결 확인 |
| 검토 요청 취소 | 버튼 클릭 시 브라우저 네이티브 확인창에서 CUA focus 명령이 시간 초과. `getJsDialog`는 undefined이고 상태/닫기도 응답하지 않아 **최종 수동 취소는 미확인**. 사용자에게 로컬 확인창 닫기를 요청했다. 제품 취소 실패로 단정하지 않음 |

첫 file chooser 시도는 label의 공백이 실제 DOM과 달라 이벤트를 기다리다 도구가 초기화됐다. 복구 후 실제 `input[type=file]`를 사용하자 파일 선택·업로드가 성공했다. 이를 제품 파일 업로드 결함으로 세지 않는다.

접수 취소·종결 상태는 [실제 인증 HTTP](../2026-10-06-owner-task-http/README.md)에서 성공/재시도/후속 변경 거절까지 확인했지만 위 수동 확인창 조작의 통과로 확대하지 않는다. 앞선 수정 전 빌드의 **참가 신청 취소**는 실제 화면에서 완료까지 확인했고, 이번 빌드의 **참가 취소 → 다시 신청**은 [인증 HTTP와 실제 SSR](application-reapply-http.json)에서 새 제목·버튼·정상 재신청을 확인했다. 최초 검사 도구가 revision을 1로 가정해 412가 발생한 뒤, 현재 GET revision을 사용하는 정상 복구 절차로 검증했다. 제품 오류가 아닌 fixture 가정 오류였다.

생성 후 새 접수 초기화·코드 복원, 첫 방문/모집 안내·전역 검색 Enter 이동은 [본문의 수정 전 연속 검증](README.md)에 기록했다. 이번 변경은 그 클라이언트 흐름을 바꾸지 않으며 API 문제를 보완한다. 실기기·스크린리더 전 조합·최대 부하는 미확인이다.
