# 직접 브라우저 조작 기록과 도구 한계

2026-10-05~06 KST, Codex in-app Chromium/CUA에서 확인했다. 실제 회원 데이터 쓰기는 하지 않았으며 저장 조작은 임시 PostgreSQL 18의 합성 계정에서만 수행했다.

## 확인한 사실

- 운영 기존 랭킹에서 최소 참여 수 입력을 25로 바꾸고 다른 랭킹 종류로 이동하면 URL의 기준은 0인데 입력에는 25가 남는 현상을 재현했다. 수정은 URL의 적용 기준에 따른 폼 key이며 실제 TSX 회귀와 HTTP를 연결한다.
- 수정 전 합성 환경에서 경기 접수를 만든 뒤 상단 새 결과 제출로 이동하면 URL에서 코드가 사라져도 이전 접수 폼이 남는 현상을 재현했다. `history.replaceState`만으로 서버 경로 key가 갱신되지 않는 원인을 확인했고 `router.replace`로 수정했다.
- 수정 빌드의 합성 신청 화면에서 1회차 편집 중 저장하지 않은 TOP 선택 → 2회차 전환 시 해당 회차의 JGL/ADC와 예비 선택 → 1회차 복귀 시 저장된 MID/SUP를 확인했다. 이전 회차의 임시 입력이 다른 회차에 섞이지 않았다.
- 합성 3회차 ARAM에서 주/부 포지션 입력이 없는 상태로 신청 저장을 완료했고, 내 신청 상태에 `포지션 구분 없음`이 표시되는 것을 확인했다.
- 계정 Chromium 저장·세션 갱신·412 복구·hydration 콘솔 검증은 별도 실행 로그 [account-return-hydration-after.log](account-return-hydration-after.log)에 있다. CUA 수동 조작과 같은 검사로 중복 계산하지 않는다.

## 완료로 세지 않은 조작

합성 신청의 취소 확인창을 연 뒤 CUA의 dialog 조회·닫기·탭 이동이 응답하지 않았다. 새 탭에서 입력값 조회/설정과 HTML은 확인할 수 있었지만 클릭 후 로그인·접수 생성 결과가 진행되지 않았고, 다른 경로의 스트리밍 로딩도 끝나지 않았다. 이는 이 브라우저 세션에서 더 이상 상호작용 검증을 판정할 수 없다는 도구 제한이다. 취소 성공, 접수 생성→새 접수의 최종 수동 E2E, 이후 페이지의 반응형·키보드 검사를 통과로 기록하지 않는다. 사용자에게 확인창 닫기를 요청했다.

서버의 신청 취소·제출 소유권·재시도·상태 전이는 [격리 DB/HTTP](database.log)에서 검증했고, 변경한 폼 identity·router 호출·후속 저장 잠금은 실제 TSX handler/렌더 회귀로 검증한다. 이 근거도 실제 휴대폰이나 모든 브라우저 UI의 통과를 대신하지 않는다.

운영 배포 후 공개 HTTP와 배포 ID/health 결과는 별도 `production.md`에 기록한다. 실제 iOS/Android·스크린리더·외부 공급자·신규 사용자 과업 시험은 미확인 경계로 유지한다.

## 운영 공개 도메인 후속 확인

로컬 확인창의 영향을 받지 않은 운영 공개 도메인 탭에서는 탐색·필터·클릭·키보드 조작이 정상 동작했다. [운영 브라우저 결과](production-browser.json)의 24개 공개 viewport 조건과 변경된 조회 흐름을 확인했다. 로컬 인증 후 취소·접수 생성/새 접수 등 저장 흐름의 미완료 판정은 유지한다.
