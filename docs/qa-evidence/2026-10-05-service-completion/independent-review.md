## 판단

이번 변경은 사이트의 기존 목적에 맞다. 참가 → 팀 편성 → 결과 제출 → 전적 확인에 필요한 기능은 이미 있었으나, 회차·접수 코드·로그인 복귀 문맥과 조회/종결 상태의 표시가 일부 끊어져 있었다. 새 메뉴나 기능군보다 기존 작업의 대상을 보존하고 다음 행동을 연결한 수정이 적절하다.

| 이용자 | 이번 개선의 실질 효과 | 검증을 구분할 경계 |
| --- | --- | --- |
| 처음 방문·비로그인 | 공개 참가·랭킹·기록을 살펴보고, 특정 접수/작업으로 로그인 후 돌아갈 수 있음 | 실제 신규 이용자의 과업 성공률은 측정하지 않음 |
| 승인 대기·이용 제한 회원 | 제출 불가능한 폼 대신 계정 상태 확인 경로를 제공 | 계정의 승인·제한 정책 자체를 바꾸지 않음 |
| 일반 회원 | 회차·접수 변경 때 이전 입력이 섞이지 않고, 결과 상태·재시도·후속 이동을 이해할 수 있음 | 합성 계정 검증이며 실제 회원 데이터를 임의 변경하지 않음 |
| 관리자 | 통계 API와 화면의 정렬 기준을 맞추고 팀 초안 변경 재시도에 기존 키를 사용 | 운영 계정의 실제 승인·경기 게시·외부 발송 작업을 수행한 것은 아님 |

홈의 여섯 영역 순서와 단일 랭킹 슬라이드, 생성 이미지 아이콘/배경을 바꾸는 수정은 없다. DOM 장식을 자동 삽입하던 효과를 제거하고 기존 모션 감소 규칙을 지키는 CSS 효과로 바꾼 것은 실제 hydration 충돌 원인을 제거하는 범위다. 측정하지 않은 LCP/INP 개선이나 전반적 성능 향상으로 표현하지 않는다.

| 접수 생성 직후 새 접수 | 최초 리뷰에서 `history.replaceState`만 사용하면 서버 key가 `new`로 남을 가능성을 통합 담당자에게 전달 | 현재 `router.replace(..., { scroll: false })`로 서버 경로를 동기화하며 생성 handler 회귀가 추가됨. 실제 생성 → 새 접수 조작은 최종 브라우저 근거로 별도 확인 |
| 접수 생성 후 경로 전환 대기 | 보안 담당자의 후속 재검토에서 생성 API 완료와 서버 경로 commit 사이에 후속 업로드가 가능해지는 P2 경합을 발견 | `navigationPending`과 API pending을 합쳐 입력·업로드·수정·취소·이어하기를 잠금. 수정 전 실패를 재현했고 직접 handler 호출도 추가 요청·확인창·파일 읽기를 시작하지 않고 전환 완료 후 다시 활성화하는 회귀 6개가 통과. 이후 전체 check도 통과했으며 실제 브라우저와는 구분 |

| MMR 페이지·점수 | 저장소는 pagination과 포지션별 정렬을 이미 제공하지만 UI 연결·표시가 빠져 있었음 | 이전/다음은 검색·포지션·pageSize를 보존. 집계 없음/검색 없음/범위 이탈/조회 실패를 분리. 선택 포지션 점수·표본의 0도 그대로 표시 |

| 화면 효과 | streaming markup이 hydration 되기 전에 하위 DOM 속성을 변경 | Mutation/Intersection observer 기반 장식을 제거했으며 읽기·스크롤 진행/직접 포인터 효과만 남김. 경고를 숨기거나 임의 대기로 우회하지 않음 |

후속 재검토에서 발견한 경로 전환 경합은 수정했고, 현재 검토 범위에서 확인된 미수정 중대 오류 또는 명확한 핵심 과업 방해 요소는 없다. 이 판정은 아래 검증 범위에 한정되며 브라우저·배포 완료를 뜻하지 않는다.

## 근거와 확인 범위

- [최종 `npm run check`](check.log)는 경로 전환 잠금 보강 후 exit 0으로 확인했고 lint/typecheck/ERD/계약/단위/아트/production build 완료를 재확인했다. 계약 463개, 단위 1,045개 통과와 환경 조건부 skip 1개, 기존 lint 경고 58개를 구분한다. QA 조회 도구의 정규식 `s` flag가 저장소 TypeScript target과 맞지 않던 검사 오류는 동등한 범위 표현으로 수정했고 전체 검사를 다시 통과했다. 이 환경/도구 오류를 제품 결함으로 추가 집계하지 않는다.
- [격리 DB 로그](database.log)의 exit 0과 인증·관리자 비밀번호·플레이어·시즌·계정 HTTP 결과를 확인했다. DB/HTTP/fake adapter가 무엇을 검사하는지는 [보안·데이터 점검](security-data-audit.md)의 기능군별 표를 따른다.
- [최종 페이지 HTTP](local-http.json)는 통합 빌드에서 합성 로그인 세션으로 108개 페이지·169개 주소 조건을 통과했다. [baseline HTTP](baseline-local-http.json)는 수정 전 비교 근거로 분리 보존한다. 어느 기록도 모든 버튼의 업무 시나리오를 뜻하지 않는다.
- [서비스 조회 HTTP](local-service-http.json)는 익명 GET 31개로 홈 순서·접수 복귀 링크·MMR 페이지/검색/잘못된 주소·공통 랭킹 순서·보호 API의 400/401·health를 확인했다. 실제 API 쓰기나 사용자 브라우저 조작을 대신하지 않는다.
- [계정 복귀·hydration 재검증](account-return-hydration-after.log)에서 실제 Chromium 계정 저장·갱신·412 복구·콘솔 점검과 강제 비밀번호/중첩 복귀 통과를 확인했다.
- [Top API 수정 후 기록](stats-top-after.log)에서 실제 격리 HTTP의 정렬/동률/빈 조건/잘못된 입력 통과를 확인했다. 이는 [수정 전 실패](stats-top-before.log)와 같은 결함의 후속 결과이며 별개 결함 두 건으로 세지 않는다.
- [직접 브라우저 기록](browser-observations.md)에서 회차 전환의 입력 분리와 ARAM 신청 저장을 확인했다. 취소 확인창 이후 CUA 세션이 응답하지 않아 취소·접수 생성→새 접수 최종 수동 E2E·후속 viewport/키보드는 완료로 세지 않는다. 후보/운영 배포 역시 이 문서 작성 시점에 완료로 판정하지 않는다.

## 인벤토리의 완전성과 크기

[JSON 원장](feature-inventory.json)을 실제 트리와 다시 대조했다. `page.tsx` 108개와 API/호환 `route.ts` 275개, 합계 383개가 모두 포함되어 누락·없는 소스·중복 URL이 없었다. metadata 3개를 더한 총 386개 경로에는 export method와 소스/검증 포인터를 기록했다.

상세 원장은 사용자가 요청한 실제 메뉴·버튼·API까지 빠짐없는 목록을 만들기 위한 산출물이다. 조작 요소 1,088개와 메뉴 상수 138개를 파일/행/표현식/동작과 연결했으며, 조작 요소 배열 자체는 약 438KB다. 나머지는 각 경로의 공통 UI 파일·검증 포인터·최종 실행 상태를 포함한다. 검사 범위 밖인 경로에는 중복 설명 대신 상태만 저장한다. 앱 소스에서 원장을 import하지 않으므로 런타임 번들에 원장 크기가 추가되는 구조는 아니다. 기능 누락을 숨기는 요약만 남기기보다 상세 원장과 읽기 쉬운 [Markdown 요약](feature-inventory.md)을 함께 보존하는 범위가 정당하다.

다만 소스 조작 위치는 실제 렌더 인스턴스 수나 버튼별 E2E 수가 아니다. 동적 이름·아이콘·숨은 입력 등 정적 추출로 이름이 없는 항목을 곧바로 접근성 오류로 판정하지 않았고, 반대로 소스 이름이 있다는 이유로 접근성 통과로 표시하지도 않았다. 관련 테스트 파일 목록은 검증 가능한 위치이며 실행 통과 주장과 구분된다.

## 문서 정합성과 남은 경계

README의 발견 사항·정책 유지·미확인 항목은 현재 변경 범위와 일치한다. 앞서 확인한 보안 점검의 Top API 진행 문구도 `stats-top-after.log`의 실제 PASS로 갱신되어 문서 불일치가 해소됐다. 접수 생성 직후 새 접수 문제는 서버 경로 동기화로 원인을 수정했고 후속 검토에서 발견한 경로 전환 중 업로드 경합도 transition 잠금과 회귀로 보강했다. 보강 후 전체 필수 검사는 통과했으며 검토 범위에서 확인된 중대/주요 과업 방해 결함 중 미수정으로 남긴 항목은 없다. 미완료 브라우저 과업·배포·운영 확인은 별도 완료 조건이며 최신 운영 ID와 source는 최초 baseline과 구분해 기록해야 한다.

추가 기능군을 만들지 않는 판단도 타당하다. 현재 파티 모집의 원본인 카카오 양식과 경쟁하는 별도 작성 시스템, 범용 게시판·채팅, 새로운 Riot 공급자를 추가할 필요를 입증한 과업 실패는 확인하지 못했다. 기존 신청·팀·제출·미디어/문의 흐름을 먼저 연결하는 편이 사용법과 유지 비용을 늘리지 않는다.

다음은 완료 범위 밖으로 남긴다: 실제 신규 이용자 테스트, iPhone/Safari·Android 설치 앱·스크린리더 전 조합, 실제 이동통신/오프라인과 운영 최대 규모 부하, Riot RSO/실계정 장애·동의, 카카오 실기기 송수신/절전/재시작, Blob 실제 provider 왕복, 외부 알림/경보 수신, 검색 서비스 소유권. 기존 계약/합성 환경 검증을 이런 외부 조건의 통과로 확대하지 않는다.

이 재검토는 소스와 확인된 검사 범위에서 추가 기능·대규모 변경을 할 근거가 없다는 판단이다. 최종 브라우저·배포·운영 확인이 끝나기 전에 서비스 개선 전체를 완료 선언하는 근거로 사용하지 않는다.
