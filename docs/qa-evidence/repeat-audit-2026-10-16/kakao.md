## 1. 예비 삭제가 본 참가자를 취소하는 문제

- 재현: 본 참가자 `합성참가자`만 존재할 때 `내전상세 7 예비삭제 합성참가자`를 보낸다.
- 원인: 분류기와 canonical command에는 `reserve: true`가 있지만 dispatcher가 `REMOVE_PARTICIPANT`로 변환할 때 누락했다. 저장소도 이름만 검색하여 본 참가자를 취소했다.
- 수정: 예비 여부를 저장 명령까지 전달하고, 명시적인 예비 삭제는 `reserve` 행만 대상으로 검색한다. 일반 `삭제`는 기존처럼 본 참가자와 예비를 모두 찾는다.
- 수정 전 단위 재현: 저장소에 전달하는 명령에서 `reserve: true`가 누락되어 실패했다.
- 검증: `예비삭제`, `대기 삭제`, 일반 `삭제`의 분류→dispatch 전달을 검사했다. 실제 DB 계약에서 예비만 삭제하려는 이름이 본 참가자에만 있으면 취소 수가 0이고 본 참가자 원본 행 전체가 그대로임을 확인했다. 실제 예비 삭제와 뒤이은 일반 본 참가자 삭제도 성공했다.

## 2. 빠른 파티 참가가 자모 닉네임을 바꾸는 문제

- 재현: `상세 3 추가 ㅁㅂㅅ` 또는 `상세 ABCDE-23456 추가 ㄱㅏ`를 보낸다.
- 원인: 공통 입력 경계는 호환 자모를 보존하지만, 빠른 편집 분류기가 전체 문자열에 NFKC를 다시 적용해 `ㅁㅂㅅ`을 `ᄆᄇᄉ`, `ㄱㅏ`를 `가`로 바꿨다.
- 수정: 이 중복 정규화는 NFC로 제한했다. 이미 정규화한 전각 코드·숫자는 유지하고, 분해 한글 명령은 계속 인식한다.
- 수정 전 단위 재현: 입력 이름 `ㅁㅂㅅ`과 canonical command의 `ᄆᄇᄉ`이 달라 실패했다.
- 검증: 번호, 고정 코드, 전각 고정 코드와 `ㅁㅂㅅ`·`ㄱㅏ`·`별빛 ㅋㅋ` 조합이 분류→canonical→파티 도메인 저장까지 원래 표기를 보존한다. 기존 전각/분해 한글, 안전하지 않은 이름 거부 테스트도 통과했다.
