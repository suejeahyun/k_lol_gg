## 판정 요약

### 소스와 로컬 검증에서 확인됨

- 구인 운영일은 KST 오전 6시를 경계로 계산한다. 오전 5시 59분 59초까지는 전 운영일, 오전 6시부터는 새 운영일이다.
- 운영일 전환은 기존 행을 삭제하거나 강제 마감하는 작업이 아니다. 새 운영일의 조회·번호 해석 범위에서 이전 운영일 구인을 제외하는 논리 리셋이다.
- 번호가 있는 구인 양식 반영, 빈 슬롯 삭제, 모집 마감 뒤에는 mutation 결과와 최신 전체 구인 현황을 한 응답에 이어서 표시한다.
- 후속 현황 조회가 실패해도 이미 성공한 추가·수정·삭제·마감 결과를 실패로 되돌리지 않고, 사용자가 `구인현황`을 다시 입력할 수 있게 안내한다.
- 구인 양식은 번호 뒤 `.`, `)`, 이스케이프된 `\.`, 공백, 들여쓰기와 전각 구두점을 허용하며 이름 뒤 포지션·메모를 보존한다.
- 내전 신청은 대소문자 포지션, `ALL`, `Mid all`, `TOP, MID`, 부라인 공란, 이름만 있는 부분 행, 번호 들여쓰기와 번호 뒤 공백을 처리한다.
- 내전 양식의 같은 슬롯이 중복되면 마지막 행을 기준으로 한다. 마지막 행이 빈 행이면 해당 슬롯을 취소하고, 번호 행 자체가 빠졌으면 기존 상태를 보존한다.
- 해석 가능한 정상 행은 저장하고 불완전하거나 충돌하는 행만 기존 확인 필요 대기열로 분리한다. 한 행의 오타 때문에 전체 snapshot이 HTTP 400으로 중단되지 않는다.
- 서로 다른 이름·닉네임이 같은 플레이어로 해석될 때 첫 슬롯은 유지하고 이후 슬롯은 확인 필요로 분리한다.
- 같은 방·같은 날짜·같은 회차·같은 모드의 `KAKAO/APPLIED` 행만 빈 행 취소 대상이다. `SITE`, `CONFIRMED`, 다른 방의 신청은 보존한다.
- 기존 V1 사용자 입력·출력 순서와 단일 서명 요청 경계를 유지한다.

### 아직 확인되지 않음

- 미커밋 작업 트리이므로 최종 Git SHA와 tag가 없다.
- Vercel preview/production 배포와 운영 health 확인을 수행하지 않았다.
- R15 또는 R6 파일을 실제 휴대폰에 복사하거나 MessengerBot R에서 컴파일하지 않았다.
- 두 실제 Kakao 방에서 여러 사용자가 구인과 내전 양식을 보내는 E2E를 수행하지 않았다.
- 운영 환경의 응답시간 p50·p95와 HTTP 400 감소 폭은 측정하지 않았다.

## 변경 범위

### 1. 오전 6시 운영일 경계

`recruitingOperatingDateKey()`가 서명된 명령 시각을 KST 오전 6시 기준 운영일로 변환한다. 생성·수정·삭제·마감 대상 해석과 후속 전체 현황 조회는 같은 명령 시각을 사용한다. 따라서 경계 직전 요청이 처리되는 동안 시계가 오전 6시를 지나도 mutation과 조회가 서로 다른 운영일을 보지 않는다.

이 동작은 논리적인 조회 범위 전환이며 데이터 삭제가 아니다. 이전 운영일 행의 보존·감사·복구 가능성을 유지한다.

### 2. 구인 mutation 뒤 전체 현황

다음 mutation 성공 응답 뒤 최신 `K-LOL.GG 구인구직 현황`을 이어서 표시한다.

- 참가자가 채워진 양식의 신규 저장
- 기존 모집의 참가자 추가·수정
- 슬롯을 비운 양식의 참가자 삭제
- `번호ㅉ` 형식의 모집 마감

후속 조회에는 mutation 요청과 분리된 receipt 범위를 사용한다. 조회만 실패한 경우 mutation 성공 문구는 유지하고 `조회 실패. 구인현황을 입력해 주세요.`를 표시한다.

`2인파티`, `5인파티` 같은 빈 양식 생성은 기존처럼 양식만 반환한다. 참가자가 입력된 전체 양식을 다시 보낼 때 저장된다.

### 3. 구인 입력 내결함성

| 입력 변형 | 결과 |
|---|---|
| `1. 이름` / `1) 이름` / `1 이름` / `1\. 이름` | 같은 번호 행으로 인식 |
| 들여쓰기·전각 숫자·구두점 | 정규화 후 인식 |
| `이름 포지션`, 괄호·쉼표·태그·메모 | 한 참가자의 표시 이름/추가 정보로 보존 |
| 빈 번호 행 | 해당 슬롯 삭제 |
| 참가자가 없는 자동번호 양식 | 새 모집을 만들지 않음 |

### 4. 내전 참가 신청 HTTP 400 복구

| 입력 변형 | 결과 |
|---|---|
| `1.지오/G/E/AD/Mid` | 주라인 `ADC`, 부라인 `MID` |
| `2.동휘/M/M/Mid all` | 주라인 `MID`, 부라인 없음 |
| `3. 재현/M/M/TOP, MID` | 주라인 `TOP`, 부라인 `MID` |
| `4 이름만` | `ALL` 안전 기본값으로 확인 필요 |
| 부라인 공란 | 유효한 빈 부라인 |
| 알 수 없는 포지션 | 해당 행만 확인 필요 |
| 같은 슬롯이 여러 번 존재 | 마지막 행이 권위 있음 |
| 마지막 중복 행이 빈 행 | 해당 슬롯 취소 |
| 슬롯 번호 행 누락 | 기존 슬롯 보존 |
| 같은 플레이어의 다른 별칭 중복 | 첫 슬롯 반영, 이후 슬롯 확인 필요 |

정상 행과 확인 필요 행을 분리하므로 일부 입력 문제 때문에 전체 요청이 일반 HTTP 400으로 끝나지 않는다. 이름도 추출할 수 없는 행은 안전하게 기존 슬롯을 보존한다.

## 데이터 안전 경계

- 스키마 또는 SQL migration을 추가하지 않았다.
- migration head는 `0036_flowery_hairball`이다.
- 오전 6시 운영일 전환은 `DELETE`, `TRUNCATE`, 일괄 `UPDATE`를 실행하지 않는다.
- 내전 취소는 같은 시즌·신청일·회차·방·모드의 `KAKAO/APPLIED`만 대상으로 한다.
- `SITE`, `CONFIRMED`, 다른 방·회차·모드의 신청은 변경하지 않는다.
- 불완전 행은 새 테이블이 아니라 기존 확인 필요 대기열과 감사 경계를 재사용한다.

## 릴리스 전 필수 확인

1. 공유 작업 트리의 다른 변경과 충돌을 검토하고 기능 commit을 만든다.
2. 기능 tag와 `docs/releases/registry.json` 항목은 실제 commit이 생긴 뒤 별도 등록한다.
3. Vercel 배포 ID·불변 URL·운영 alias·health를 실제 값으로 기록한다.
4. 선택한 휴대폰 설치본의 SHA-256을 재계산하고 MessengerBot R 컴파일을 확인한다.
5. 실제 구인방에서 빈 양식 생성 후 참가자 입력, 수정, 빈칸 삭제, 타 사용자 마감, 전체 현황을 확인한다.
6. 실제 기능방에서 정상 내전 행, 이름만 행, `Mid all`, 중복 슬롯, 빈 행 취소와 저장 결과를 확인한다.

## 롤백

DB migration과 데이터 삭제가 없으므로 schema rollback은 필요 없다. 문제가 생기면 서버 코드를 직전 확인된 배포로 되돌리고 휴대폰 설치본을 직전 확인 파일로 교체한다. 이미 저장된 모집·신청·receipt·감사 이력은 임의 삭제하지 않는다. 오전 6시 경계 또는 후속 현황 문제가 원인이면 해당 소스 변경을 forward-fix하거나 직전 서버 배포로 되돌린 뒤 같은 경계 테스트를 다시 실행한다.
