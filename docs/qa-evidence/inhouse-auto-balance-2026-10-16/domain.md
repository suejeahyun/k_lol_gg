## 정책과 API

- 기존 등록 가능 포지션과 바텀 현재 티어 제한을 만족하는 후보가 하나라도 있으면 기존 탐색과 정렬 결과를 유지한다.
- 엄격 탐색에 후보가 없을 때만 전체 역할을 탐색한다. 원래 주·부 포지션과 허용 포지션은 보존하고, 미등록 역할에는 기존 AUTO 점수 계산을 적용한다.
- 완화 탐색의 정렬은 바텀 티어 위반 수 → 제한 초과 단계 합 → 미등록 역할 인원 → 기존 안전성 및 규칙 1→6 우선순위 → 기존 수치 비용 → 결정적 서명 순서다.
- 구조 조건인 서로 다른 10명, 팀마다 5명, 각 역할 1명은 완화하지 않는다. 개인 점수·MMR 계산식과 입력값은 변경하지 않는다.
- `evaluateTeamBalanceLayout(players, layout, { allowConstraintRelaxation: true })`에서만 같은 완화 정책으로 수동 배치를 평가한다. 기본값은 엄격 검사다.
- 실제 완화가 있는 결과에만 `score.fairness.constraintRelaxation`을 기록한다. `applied`, `roleDeviationCount`, `bottomTierViolationCount`, 그리고 조건·선수 ID·포지션·설명으로 구성된 `reasons`가 포함된다. 상태는 `REVIEW_REQUIRED`, 해당 조건 검사는 `WARN`이다. 구조가 잘못된 배치를 유효한 결과로 바꾸지 않는다.

주요 회귀 근거:

1. 10명 모두 TOP만 등록한 입력에서도 완성된 한 후보를 반환한다. 미등록 역할 8명, 바텀 위반 0, 원본 입력 JSON 불변을 확인했다.
2. 역할 충돌이 있는 입력에서 독립적인 10자리 배정 DP가 계산한 전역 최소 이탈 1명과 실제 추천이 일치한다. 역순·회전 입력에서도 후보 전체가 동일하다.
3. 완화 탐색은 `126 × 120 × 120 = 1,814,400`개 배치를 검사한다. 기존 전체 역할 탐색 회귀도 통과했다.
4. 바텀 티어 차이를 다른 역할 배정으로 피할 수 있는 경우 바텀 제한을 지키는 후보를 선택한다. 원래 역할로 수동 평가하면 바텀 위반 1건을 정확히 기록한다.
5. 독립 정렬 oracle에서 바텀 위반·초과량·역할 이탈 우선순위와 규칙 1→6·기존 비용·서명 순서를 함께 비교했다. 20개 결정적 무작위 사례 각각 25쌍의 상위 3개가 일치했다.
6. 엄격 조건이 가능한 16개 배치를 별도로 열거해 기존 선택 순서와 같은 후보인지 확인했다. 완화 2차 탐색과 표식이 생기지 않는다.
7. 자동 추천 점수와 같은 배치의 명시적 완화 수동 평가 점수가 정확히 같다. 기본 수동 평가에서는 기존 제한을 계속 적용한다.
8. 인원 수·중복 선수·역할 누락은 완화 옵션을 켜도 거부한다. 점수와 기존 현재/최고 티어·개인 점수 보정 골든 회귀를 유지했다.

## 저장·화면 연결 독립 검토

읽기 전용으로 repository와 workspace/share 연결을 확인했으며 확정 결함을 발견하지 않았다.

- 서버는 현재 회차의 AUTO rank 1에 실제 완화 표식이 있을 때만 완화를 허용한다. 클라이언트 요청이나 수동 후보의 표식으로 엄격 회차를 완화하지 않는다.
- 자동 선택과 저장은 현재 회차 후보를 조회한 뒤 권위 있는 참가자 입력으로 재검사한다. 수동 선택도 같은 정책 helper를 사용한다.
- 재평가는 원본 `eligiblePositionsJson`을 다시 읽으며 참가자의 rating snapshot만 갱신한다. 새 회차가 엄격 조건을 만족하면 이전 회차의 완화 표식이 전달되지 않는다.
- 화면의 교체·미리보기·412 수동 유지 검사는 각 대상 초안의 현재 회차 AUTO 표식을 사용한다. 완화 경고가 있는 결과도 선택·저장·복사를 진행할 수 있고, 선수명과 배정 포지션 및 바텀 조건을 표시한다.

격리 DB의 실제 선택·저장·수동·재평가 회귀는 [database.md](database.md)에 별도 기록한다. 이 문서는 운영 배포 완료 증빙이 아니다.
