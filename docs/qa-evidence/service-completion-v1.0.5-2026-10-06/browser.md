# 실제 과업 확인 — 진행 기록

기준 source `ca242292`/운영 runtime `583dab4d`에서 시작했다. CUA 브라우저와 일회성 PostgreSQL/최적화 빌드를 사용한다. 실제 회원·운영 신청·경기는 변경하지 않는다. 이 문서는 실행 시점과 새 빌드 확인을 구분한다.

## 수정 전 실제 재현과 추가 과업

- 운영 검색 320px에 공백 없는 영문 80자를 입력: 플레이어 검색 링크 rect x=40..280, computed overflow-wrap=anywhere. 넘침 후보는 재현되지 않아 수정하지 않았다. [검색 화면](search-before.jpg).
- 운영 랭킹 로딩 종료 뒤 기준 적용 버튼에서 Shift+Tab: 최소 참여 입력의 실제 포커스는 `rgba(103,166,227,0.45) solid 3px`, 배경 흰색. 별도 색 대비 계산과 일치했다. 운영 이름 strong의 overflow-wrap은 normal, 이름 칸은 137px였다. 긴 이름 겹침은 합성 자료로 별도 재현한다.
- 합성 일반 계정 로그인→팀 도구 복귀→저장한 팀→저녁 내전 열기. 블루 탑 S06플레이어1과 레드 탑 S06플레이어6을 교체하면 화면 블루는 6이지만 복사한 BLUE 첫 선수는 1이었다. 경기 접수 링크도 이전 팀을 대상으로 활성 상태였다. [교체 화면](team-before.jpg). 단순 코드 추정이 아닌 실제 클립보드로 불일치를 확인했다.
- 새 팀 도구에서 `S06플레이어` 검색→합성 10명 직접 추가→저장된 주 포지션(각 2명) 확인→추천 생성→선택 팀 저장→저장됨→새로고침→경기 결과 접수 이동. 생성한 초안 ID가 URL에 유지되고 접수 제목/연결 팀에 `오늘의 내전`이 나타났다. 이 실행은 후속 dirty 잠금 패치 전 빌드다.
- 문의 폼에 합성 이름/회신 불필요 연락 방법/검증 내용 입력→합성 환경의 동의→접수 완료 및 접수번호 표시. 외부 발송은 없고 일회성 DB만 저장했다. 합성 관리자 로그인→운영 신청서로 복귀→같은 접수번호 상세에서 내용 일치 확인.
- 해당 문의를 검토 중으로 바꾸고 메모 저장: **`If-Match 값이 올바르지 않습니다.`** 오류로 저장 불가. 실제 UI의 `rev-0` 형식이 API의 숫자 ETag 계약과 달랐다. API 실행기가 정상 숫자를 보내 통과했던 검사와 별개인 UI 결함이다. 처음 exact label selector 실패는 label 내부 option 문자열을 읽고 regex selector로 교정한 도구 문제이며 제품 결함 수에 포함하지 않는다.
- 관리자 플레이어 검색→합성 S06플레이어1 수정→실제 maxlength=16인 게임 이름에 W 16자 입력→저장 후 이름·변경 버전 1 반영 확인. 실제 회원은 변경하지 않았다. 현재 기본 시즌은 집계 대기, 공개 통계 시즌은 빈 랭킹이므로 이것을 긴 이름 순위 검증 통과로 계산하지 않는다.

## 새 빌드 확인

첫 통합 `npm run check` 통과 후 새 disposable PostgreSQL과 최적화 서버 `127.0.0.1:60301`을 사용했다. 아래는 이 빌드에서 실제 실행한 결과이며, 이후 랭킹 CSS 보완의 확인은 별도로 추가한다.

- 긴 이름 전용 ENDED 시즌의 READY 합성 projection에서 영문 W 16자/한글 16자 두 선수를 표시했다. 320px에서 영문 이름은 link width 137px/scrollWidth 240px, strong x=69..309, 성적 셀 시작 x=218이었다. 실제 승률과 겹치고 카드 끝에서 잘렸다. [수정 전 화면](ranking-long-before.jpg). 한글은 줄바꿈됐다. `.board li a`와 `.podium a`에 기존 MMR의 `min-width:0; overflow-wrap:anywhere`를 적용했다. 이는 표시 fixture이며 실제 경기 집계를 검증한 데이터로 세지 않는다.
- 비로그인 상태에서 실제 유효한 초안 `?tab=recommendations&team=RED`를 열어 로그인 URL의 encoded next 보존, 합성 계정 로그인 후 같은 URL·RED 팀 추천 화면 복귀를 확인했다. 앞서 검증자가 잘못 사용한 `tab=manual`은 허용 query가 아니므로 복귀 결함으로 세지 않는다.
- 같은 초안의 팀 배치에서 블루 탑1/레드 탑6을 교체했다. `수동 변경 · 평가 필요`가 나타나고 팀 복사·통계 재평가·경기 접수는 비활성, 되돌리기는 활성이다. `선택한 배치로 되돌리기`로 기존 배치와 접수 링크가 돌아왔다.
- 다시 교체→`수동 배치 평가·선택`→실제 클립보드: BLUE 첫 선수6, RED 첫 선수1로 화면과 일치했다. 선택 팀 저장→저장됨→새로고침 후에도 블루 탑6과 저장됨을 확인했다. [저장 뒤 화면](team-after.jpg). 경기 접수 링크는 올바른 draftId로 이동했으나 로딩 종료 전에 다음 과업으로 이동했으므로 이번 실행에서 접수 폼의 팀 표시까지 확인했다고 쓰지 않는다. 이전 기준 빌드에서 폼 연결은 확인했다.
- 참가 신청의 본 참가1/10·미드·부서폿 상태에서 `내 신청 취소`를 눌렀으나 브라우저 입력 명령이 시간 초과됐다. 소스에는 정상 `window.confirm`이 있으며 도구의 dialog 조회는 undefined, 기존 탭은 이후 상태/닫기 명령도 시간 초과였다. 새 탭에서 여전히 신청1을 확인했으므로 취소 완료로 기록하지 않는다. 다른 탭의 입력/제출도 진행되지 않아 사용자에게 확인창/검증 탭 닫기를 요청했다. 이 도구 제한을 제품 결함으로 단정하거나 confirmation을 스크립트로 우회하지 않았다. 기존 DB·HTTP의 취소 경계 검증과 실제 UI 미완료를 구분한다.
- 문의 검토 상세의 관리자 로그인 next까지 도달했다. 입력은 채웠지만 위 브라우저 입력 제한으로 제출/처리 완료는 확인하지 못했다. handler와 관리 HTTP 통과가 이를 대신하지 않는다.

이 fixture의 전체 DB 계약, 확대된 이벤트 DB 동시성, 이벤트 실제 HTTP 11응답, 전체108페이지/169조건은 통과했다. `stop` 명령 뒤 harness exit0·cluster 중지·일회성 경로 정리까지 확인했다. [DB 로그](completion-browser-final-database.log), [이벤트 HTTP](event-write-http-after.json), [전체 조회](release-http.json).

## 랭킹 보완 후 최종 렌더

마지막 CSS 수정까지 포함한 `check-final.log` exit0 이후 새 disposable fixture의 `127.0.0.1:64915`에서 확인했다. 동일 입력 계약의 W16/한글16/Riot ID를 320·390·768·1280px로 측정했다. 모든 폭에서 문서 가로 넘침 없음, 링크 scrollWidth=clientWidth, 이름과 첫 수치 칸 겹침 없음, 상위 카드 안의 잘림 없음이다. 320px 이름 오른쪽206px/성적 시작218px로 분리되고 이름은 여러 줄로 표시된다. [측정](ranking-layout-after.json), [화면](ranking-long-after.jpg).

브라우저가 locator에 포커스를 놓고 screenshot/DOM 조회는 수행했지만 실제 키 입력은 앞선 확인창 제한을 유지했다. 이 관측을 키보드 순차 탐색 통과로 확대하지 않는다. 실제 생성/취소/관리 상태 변경 UI 중 도구로 수행하지 못한 항목은 위 기록과 같이 남는다. 컴포넌트 실제 handler와 격리 HTTP/DB는 각각 통과했으나 이것을 브라우저 조작 완료라고 쓰지 않는다.
