# 사이트·카카오 봇 재점검 보완 1.0.0

사용자가 [재점검의 9건](../site-kakao-reaudit-2026-10-14/README.md)에 대해 “진행해줘”라고 승인한 범위다. 선행 점검은 수정 전 기록으로 보존한다. 이 문서는 구현·검증·배포·휴대폰 설치 상태를 구분한다.

## 변경 범위

1. 공개 모집 목록에 모집일과 고정 코드를 전달하고 카드의 복사 명령은 코드를 사용한다. 코드 없는 기존 모집은 날짜·게임·참가자를 대조하도록 안내한다. 공개 GET은 코드나 복사 원본을 발급하지 않는다.
2. 웹 참가 신청·취소는 화면의 시즌, 운영일, 회차 UUID, 본인 신청 UUID를 요청에 포함한다. DB 트랜잭션에서 현재 대상과 대조하며 대상이 바뀌면 입력을 보존하고 새로고침·확인을 요구한다. 대상 정보 없는 구버전 웹 요청은 428로 거부한다.
3. 모집 명령의 운영일, 양식 발급과 만료 판단은 서버 시각을 사용한다. 휴대폰 timestamp는 HMAC·요청 유효시간·감사용 값이며 업무일 선택에 사용하지 않는다. event ID와 원본 요청 digest의 멱등성은 유지한다. 번호·코드의 참가·삭제·마감 재전송은 인증된 기존 receipt를 먼저 확인해 같은 번호의 다른 날짜 모집으로 바뀌지 않으며, 원본 발급 시각은 현재 서버 시각을 유지한다.
4. V4 서명 검증 후 매 요청마다 운영 설정을 읽는다. 전체 비활성·유지보수는 전체 gateway, 개별 스위치는 해당 명령군을 차단한다. 설정 조회 실패도 실행하지 않는다. 차단 결과를 성공 receipt로 보관하지 않으며, 이미 처리된 요청의 재전송도 현재 설정을 확인한다.
5. 휴대폰 답장 실패와 일시적인 오류 안내는 결과 전달 완료로 기록하지 않는다. 서버 성공 후 전달된 답장은 기존처럼 중복을 억제한다.
6. 파티의 명시적 예비 추가 의도를 번호·고정 코드 경로 모두 저장까지 보존한다.
7. 경기 접수 412 충돌 시 최신 접수를 조회하고 초안을 보존한다. 편집 중 이미지 업로드 오류 후 최신 revision을 확인한 경우에도 동일 비교를 요구한다. 최신값을 확인한 뒤 입력 유지 또는 버리기를 선택해야 다시 저장한다.
8. 사이트·카카오 관리자 설정은 저장 대기 중 입력을 잠가 응답으로 추가 입력이 사라지지 않도록 한다.
9. 휴대폰의 내전 마감 별칭·전각 정규화를 서버 지원 문법과 맞춘다.

## 운영 설정 대응

| V4 명령군 | 적용 설정 |
| --- | --- |
| 파티·기존 스크림 안내·운영 양식 | recruitingEnabled |
| 내전 모집·신청 | seasonApplicationsEnabled |

| 사진 상태·취소 | imageReceiveEnabled |
| 로컬 도움말·진단 | 전체 활성·유지보수만 적용 |

모든 서명 요청은 정규화한 메시지 길이 제한도 적용한다. 서버 밖에서 휴대폰 자체가 응답하는 로컬 명령은 서버 차단 설정의 대상이 아니다. 정적 installation scope와 물리 방 이름을 권한으로 사용하지 않는 ADR 0008은 유지한다.

운영 설정 [읽기 전용 사전 확인](production-policy-preflight.json) 결과 모든 기능이 활성이고 유지보수는 꺼져 있었다. 설정값은 변경하지 않았다. 스키마 변경은 없으며 migration head는 `0049_stable-recruit-codes`(50개)다.

## 검증·배포 상태

최종 검사 결과 및 정확한 source/tag/deployment는 아래와 production.md에 기록한다. 휴대폰 설치는 생성본 검증과 별도이며 실제 교체 전에는 `PENDING_USER_INSTALL`이다.

- focused UI/서비스 40/40 및 실제 시즌 HTTP의 권한·멱등성·revision·target 누락 428·대상 불일치 412 통과. 합성 PostgreSQL과 Next dev 서버는 정리했다.
- R29 공개 생성·휴대폰 VM 47/47, ES5·Rhino·Acorn 토큰 동일성 통과. 비공개 한 파일 생성·기존 R28 hash 일치 백업을 확인했다. [파일 검증값](bot-artifacts.json).
- 실제 브라우저에서 React 컴포넌트를 합성 응답에 연결해 경기 수정 충돌→입력 유지→revision 2 재저장, 두 설정 화면의 입력 잠금/해제, 날짜 변경→명시적 새 대상 선택→신청을 확인했다. [브라우저 검증 범위](browser.json), [320px 합성 화면](application-mobile.png). 사이트 공통 shell·인증·서버는 별도 검사이며 이 화면은 실제 운영 신청을 생성하지 않는다.
- Git 전체 이력 비밀정보 검사 통과. 새 소스와 증거 파일을 포함한 최종 tree 검사도 배포 전 실행한다.
- 독립 검토에서 발견한 이미지 업로드 복구의 충돌 우회를 수정하고 회귀를 추가했다. 초기 작성 중 clock fixture 문법/타입·DTO 기대값·합성 UUID 및 예비 명령 validator 누락을 검사에서 찾아 수정했으며, 초기 실패를 최종 PASS로 간주하지 않는다.

## 최종 배포 전 검사

- `npm run check`: exit 0. 계약 704/704, 단위 1,112 pass / 1 skip, lint 오류 0 / 기존 경고 58, typecheck, ERD 114 tables / 175 FK, 가이드 이미지 68개와 production build 통과.
- 격리 PostgreSQL recruiting scope: 11개 파일 112/112 PASS, skip 0. 마지막 실패는 DB 전용 과거 날짜 fixture 두 곳에 서버 시계를 주입하지 않은 테스트였으며 이를 고친 뒤 전체 scope를 다시 통과했다. 런타임 소스 변경은 없었다. [DB 상세 근거](data.md).
- 중복 요청의 최초 조회가 원 요청 커밋보다 빨랐던 경합까지 검사했다. 이미 처리된 명령의 답장은 재검증한 receipt의 원래 모집 UUID·날짜·번호에 고정하며, 검증할 수 없는 다른 대상으로 양식을 만들지 않는다.
- 초기 실패 로그는 최종 검사와 구분한다. 배포 후보와 운영 확인 결과는 배포가 실제 완료된 뒤 별도로 기록한다.
