# Stable recruitment code storage — local verification

- Scope: PARTY persistence only. Existing short-form storage and INHOUSE remain supported. No production access or deployment was performed for these checks.
- Migration: `0049_stable-recruit-codes`, generated by `npm run db:generate -- --name stable-recruit-codes`. Reviewed SQL contains two new tables, one FK between those tables, and three indexes; it does not modify or delete existing tables/data. ERD regenerated and checked: 114 tables, 175 FKs.
- Registry: `recruiting.kakao_recruit_codes` permanently binds a unique readable code to an authorized installation hash and real party UUID. Issuance never rewrites that identity. `last_version` remains after snapshot cleanup, preventing expired reference reuse. The application checks party authorization/status separately; a public code grants no permission.
- Creation ordering: the authorized party transaction can issue a code before inserting its party. Therefore `target_id` is UUID typed without an immediate FK to `parties`; the existing transactional authorization/aggregate logic remains responsible for that target. The snapshot-to-registry FK uses RESTRICT.
- Snapshots: `recruiting.kakao_recruit_form_snapshots` retains immutable originals by code/version. Identical state within one operating day reuses its reference; changed state or a new day issues a new positive safe-integer version. Original expiry remains exactly 06:00 KST. Bounded cleanup removes at most 256 expired originals per call and keeps the registry/counter.
- Concurrent issuance: unique scope/target binding, conflict-safe insertion and a registry row lock serialize version allocation. Random code collision retry, rollback and version exhaustion are covered with actual PostgreSQL.

## Compatibility limits

The additive migration leaves the old snapshot reader/writer working, demonstrated after upgrade. This verifies database compatibility, not that an old application understands the new `code@version` transport or the new human-readable command syntax. Public routing and terminal-party behavior are verified separately by the application workstream.
