# 신규 커뮤니티 provider 실제 배포 검증

최종 소스 `dd71d851ce18473b1d9a89703374fe5cbc9bf46b`를 신규 QA Vercel 프로젝트에 배포하여 READY, 공급자가 반환한 `gitSource.sha`와 `githubCommitSha`, 실제 도메인이 가리키는 프로젝트·배포 ID를 확인했다. 익명 홈은 HTTP 200이며 runtime은 `ACTIVE`, 설정 revision은 3이다. 상세 기계 판독 결과는 [provider-live.json](provider-live.json)에 있다.

검증 대상은 이번 작업에서 만든 일회용 Neon 프로젝트, Vercel 프로젝트, private Blob 저장소와 루프백 합성 HUB DB뿐이다. 운영 HUB·KLOL·NEXUS의 계정과 자료는 변경하지 않았다.

## 실제 통과한 동작

- Neon 빈 DB 초기화 후 125개 업무 테이블을 점검했다. 기존 커뮤니티 자료를 복사하지 않았고 소유자 1명과 초기 설정만 생성됐다.
- 예상 production 도메인을 명시적으로 등록하고 소유 프로젝트·검증 상태·실제 배포 연결을 확인했다. 자동 생성 별칭이 긴 프로젝트 이름을 축약하는 실제 API 차이를 수정했다.
- DB·세션·SSO·cron·Blob 비밀 환경 변수의 production 전용 범위를 확인했다. Blob 토큰 값은 읽거나 출력하지 않았다.
- 공개 전 익명 홈/API 접근은 차단되고 소유자의 유효한 세션으로만 미리보기가 열렸다.
- 하위 사이트의 브랜드 중복 저장 API는 409로 거절되고 HUB에서 관리하도록 안내했다.
- 실제 PNG를 private Blob에 업로드했다. 인증된 원본 읽기의 SHA-256이 업로드와 일치했고 익명 읽기는 거절됐다.
- 소유자 활성화가 DB에 반영된 뒤 공개 홈이 열렸다. 중복 활성화 관찰은 새 감사 기록을 만들지 않았다.
- lounge 테마·이름·색상 및 카카오 안내 메뉴를 게시하여 실제 홈에 반영했다.
- media/recruiting을 끄면 새 생성 API는 403으로 차단되고 기존 이미지 읽기는 계속 가능했다.
- 기존 설정을 새 revision으로 복원하자 생성 기능이 다시 열렸다. 최종 소스 재배포 후에도 갤러리 2개와 READY 이미지 1개가 유지됐다. 테스트 세션은 모두 폐기했다.

## 검증 범위와 제한

최초 32초 초기화 시도는 취소되었으며 동일한 신규 DB에서 85초 제한으로 재시도하여 약 67.9초에 완료됐다. journal은 `0000`부터 `0051`까지 52개다. 이 DB는 마지막 `0051`의 중앙 `ACTIVATING` 제약 변경 전에 만들어졌으므로 **최종 migration의 새 DB 최초 적용을 실제 Neon에서 검증했다고 주장하지 않는다.** 해당 변경은 하위 runtime 필드에 영향이 없고 최종 스키마의 새 DB 적용은 별도 격리 DB 테스트 범위다.

실제 provider API는 기존 Vercel CLI OAuth를 메모리 안에서 사용하는 QA 연결로 실행했다. 이 토큰을 서버 환경에 복사하지 않았다. 전용 Vercel 서버 토큰으로 운영 HUB worker가 완주하는 검증은 이 증거에 포함되지 않는다. 운영 HUB에 QA 사이트나 계정을 등록하지 않았으므로 인증 검증에는 하위 QA DB의 짧은 소유자 세션을 사용했다. 운영 SSO 전체 경로는 별도 증거가 필요하다.

중간 QA 오류는 테스트 스크립트가 업로드 응답의 `asset.assetId` 대신 `asset.id`를 읽어 `/private-assets/undefined`를 요청한 것이었다. 실제 업로드는 READY로 완료됐다. 테스트 스크립트만 바로잡고 기존 이미지 목록·인증 원본 읽기로 성공을 확인했다.

## 정리 상태

정리를 완료했다. 실행 직전 원격 DB의 계정이 합성 소유자 1명뿐임을 확인하고 HUB 주체 매핑, QA 갤러리 2개·이미지 1개, 125개 업무 테이블의 예상하지 않은 사용자 자료 부재를 재확인했다. 신규 Vercel 1개·Neon 1개·private Blob 1개·루프백 합성 DB 1개를 삭제했다. 원격 세 리소스의 재조회는 모두 404였고 로컬 DB 목록에서도 대상이 사라졌다. 비밀과 실제 리소스 ID는 이 공개 증거에서 제외했다.

Blob 저장소는 연결을 해제한 후에도 객체가 남으면 `409 not_empty`를 반환했다. 저장소 토큰을 읽지 않고, 기존 QA 배포의 관리자 이미지 삭제 API와 보안 정리 cron으로 해시가 일치하는 127바이트 fixture 하나를 삭제했다. 이때 해당 QA fixture의 삭제 요청 시간만 8일 전으로 설정하여 7일 보존 기간 경계를 넘겼다. cron의 삭제 1건·실패 0건을 확인한 후 저장소 삭제가 성공했다. 이 절차는 운영 자료나 보존 정책을 변경하지 않았다.

도메인 및 alias 계약은 [Vercel 공식 OpenAPI](https://openapi.vercel.sh)를 확인했다. Blob 정리는 [공식 CLI 소스](https://github.com/vercel/vercel/blob/main/packages/cli/src/commands/blob/store-remove.ts)의 연결 삭제 후 저장소 삭제 순서를 따른다.
